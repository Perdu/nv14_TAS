# n v1.4 TAS replay optimiser

This script combines a deterministic Python emulator for the relevant parts of
**n v1.4** with three replay-search strategies. The code was almost entirely 
generated by GPT 5.6.

- **`auto`** improves a known, completed whole-level speedrun or highscore replay.
- **`local`** optimises short sets of frames for a position or distance at a chosen frame.
- **`jump-pattern`** exhaustively searches a small number of physically successful jump pulses while preserving horizontal input.

The optimiser accepts either a combined n level/complex-replay text file or a
libTAS `.ltm` movie. It writes the result in the same format as its input, so an
LTM can be optimised and opened directly in libTAS without a separate conversion
step. The source file is never overwritten.

**Random-splice Auto:** waypoint searches run sequentially, but each uses
Local population multiprocessing (`--workers`). Per-waypoint and continuation
repair progress is shown. `--auto-stagnation-runs` stops after that many rounds
without a verified full-run improvement; `--auto-splice-repair-searches` bounds
continuation searches per waypoint. See `docs/RANDOM_SPLICE.md`.

## Examples

All of the examples below use `examples/config.toml`. For details of all the configuration option refer
to the other sections.

Auto mode is used for optimising a whole level at once. Example:
```bash
python3 optimize_replay.py auto 'examples/91-1.txt' --config 'examples/config.toml' --output 'examples/91-1_optimised.txt'
```

An .ltm file can also be used:
```bash
python3 optimize_replay.py auto 'examples/91-1.ltm' --config 'examples/config.toml' --output 'examples/91-1_optimised.ltm' --replay-output 'examples/91-1_optimised.txt'
```

Local mode is used for varying direction inputs to maximise/minimise a particular goal when the jump 
frames are already set. There are also however additional options for adding in jump mutations.

Example for corner jump power maximisation:
```bash
python3 optimize_replay.py local 'examples/cj.txt' --config 'examples/config.toml' --output 'examples/cj_optimised.txt'
```

Jump-pattern mode is used for bruteforcing all possible jump combinations within a short frame range, 
such as jumping on top of a bounceblock. This mode does not edit direction inputs.
Example bruteforcing of all 2 and 3 jump combinations on top of a bounceblock:
```bash
python3 optimize_replay.py jump-pattern 'examples/bbjump.txt' --config 'examples/config.toml' --output 'examples/bbjump_optimised.txt'
```

### Reusing Local splice files with Auto objectives

You can now layer normal TOMLs with repeated `--config` flags, and apply an
unchanged `[local]` splice objective using `--goal-config`:

```bash
python optimize_replay.py auto run.txt \
  --config default.toml --goal-config splice-167.toml \
  --auto-runs 1 --output result.txt
```

Local's search strategy is ignored by this goal-only import; it preserves the
Auto search budget from `default.toml`. The `--auto-runs 1` override is needed
when the default config has `runs = 0` because endpoint Auto requires finite
campaigns. See `docs/CONFIGURATION.md`.

## Requirements and setup

- Python **3.11 or newer**.
- On Debian, the following packages are required to build the optimiser: python3-setuptools, python3-dev and gcc.
- Building the native engine also requires Cython (`python3 -m pip install "Cython>=3.2.4,<4"`). The generated C is not stored in Git.
- No third-party Python packages are required to run the optimiser.
- Auto, Local and jump-pattern require the bundled native extension to be
  built with a C11 compiler and Python development headers. Fixed-replay tools
  and the readable reference emulator remain usable without them.
- `pytest` is required only to run the bundled test suite.
- `PyYAML` is required only for the optional corpus verification and native
  differential/coverage tools.


Extract the archive, open a terminal in the extracted directory and build the extension 
from the project directory with:

```bash
python build_native.py
```

Confirm that the command-line interface starts:

```bash
python optimize_replay.py --help
python optimize_replay.py local --help
python optimize_replay.py jump-pattern --help
python optimize_replay.py auto --help
```

On systems where `python` does not select Python 3, use `python3`. On Windows,
`py -3.11` or a newer installed version can be used in place of `python`.

The examples in this README use Bash-style `\` line continuations. In
PowerShell, put the command on one line or replace each `\` with a backtick.


## Input, output, frames and ticks

### Combined text input

A text `INPUT` must be UTF-8 and contain an adjacent n v1.4 level field and
complex replay field, normally in a record resembling:

```text
$level name#author##<level data>#<complex replay>#
```


### libTAS `.ltm` input

An `INPUT` whose suffix is `.ltm` is read as a libTAS movie. The optimiser uses
the single top-level regular-file member named `inputs`; editor branches such as
`inputs1` are not treated as the active movie. The first n replay frame is the
libTAS frame immediately after the first frame containing Space (`K20`). Setup
and menu input through that Space frame remain outside the replay and are
preserved.

The active keyboard field is mapped as follows:

| libTAS keysym | Key | n input |
|---|---|---|
| `ff51` | Left arrow | Left held |
| `ff53` | Right arrow | Right held |
| `ffe1` | Left Shift | Jump held; a rising edge generates jump trigger |

Only these three n controls are changed in output replay frames. Other keyboard
keys, mouse/controller fields and other per-frame data on retained lines are
preserved. So are archive members such as alternate input branches,
annotations and editor data, the pre-Space setup, and the movie's neutral
post-roll/padding. If an optimised replay becomes longer than the original
replay body, newly required frame lines contain only the n controls. If it
becomes shorter, output is refused rather than discarding unrelated input from
any source replay line that would be removed. The gzip/tar container is rebuilt,
so whole-file binary equality is not expected even when retained member data
is unchanged.

A raw LTM has no n level data, so the optimiser resolves a level identifier and
looks it up in `N v1.4 + NReality levels.txt`:

1. `--level-id NN-N`, when supplied;
2. an identifier embedded by an earlier output; or
3. the exact filename stem, for example `00-0.ltm` implies `00-0`.

If the name is not sufficient, pass `--level-id`. An explicit identifier that
conflicts with embedded metadata is rejected.

Use `--levels-file FILE` to select the level database directly. Otherwise the
optimiser searches for `N v1.4 + NReality levels.txt` in a few likely locations.


For a raw movie, replay length is inferred by removing trailing frames with no
Left, Right or Shift input after the Space boundary. The removed neutral frames
remain as libTAS post-roll. If that inference would also remove intentional
idle replay frames, use `--ltm-postroll N` to declare exactly how many final
rows of the active input log are padding. For example, `--ltm-postroll 3` keeps
every post-Space row except the final three, while `--ltm-postroll 0` keeps
every post-Space row in the replay. `N` must leave at least one replay frame.
The explicitly excluded rows are authoritative post-roll and are preserved
unchanged, even if they contain later keyboard or device input.

An optimiser-written LTM instead contains `nv14_optimizer.json`, tied to the
active `inputs` content by SHA-256, recording the exact replay start, tick count,
level ID and complete level record. Without an explicit post-roll override,
this preserves intentional replay-idle frames and makes later passes
self-contained; the level database is no longer needed unless `--levels-file`
is explicitly given. If libTAS or another tool later changes `inputs`, the
stale exact replay boundary is ignored with a warning and the raw-movie rules
are used again; a still-valid embedded level identity remains available.

### Output files

All optimisation commands require `-o FILE` or `--output FILE`. A text input
writes a complete combined level/replay record. An LTM input requires an `.ltm`
output and rebuilds that movie with the verified replay in its active `inputs`
member. A text input cannot produce LTM output because it provides no movie
template.

`--replay-output FILE` additionally writes only the packed replay string. It is
optional and works with either source format; a replay-only file is not itself a
valid optimiser input until it is merged into a combined record or movie.

The input, main output and replay-only output must all be different files. The
output directory must already exist. Writes use an atomic replacement, and
verified live checkpoints are used where the mode supports them.

Every LTM must contain exactly one top-level `config.ini` with one numeric value
for each of `frame_count`, `framerate_num`, `framerate_den`, `length_sec` and
`length_nsec`; both frame-rate values must be positive. The output synchronises
the frame count and duration with the edited active input log, respecting valid
per-frame libTAS timing fields where present.

### Local and jump-pattern frame convention

Frame numbers are zero-based. `--target-frame N` applies replay inputs `0`
through `N`, inclusive, then evaluates the resulting state. Thus target frame
71 means 72 input steps have been simulated.

### Auto completion convention

Auto uses n's whole-replay convention instead. A body of `N` serialized inputs
is simulated with exactly one implicit neutral input at step `N`. A canonical
Auto replay must complete on that neutral sentinel, so its finish tick is also
the number of serialized inputs written.

If the supplied replay contains unused inputs after an earlier completion, Auto
first trims them and verifies the canonical sentinel-ending form.

If the game sets completion and then kills the ninja later in the same object
collision traversal, death on that exact completion tick is accepted; a death
on any earlier tick is not.

## Quick start and choosing a mode

| Goal | Mode | Source replay requirement | What is changed |
|---|---|---|---|
| Improve a complete route automatically | `auto` | Must be a live, completed route in the selected emulator model | Whole-route semantic mutations, retimes and repairs |
| Improve position or distance at a known frame | `local` | Need only remain alive through the target frame | Small contiguous or sparse frame sets |
| Exhaustively retime a few jumps | `jump-pattern` | Need only remain alive through the target frame | Jump-held input in one continuous range; horizontal input is preserved |

## Common options

The command shape is:

```text
python optimize_replay.py MODE INPUT [OPTIONS]
```

`MODE` must be the first argument and must be `auto`, `local` or
`jump-pattern`. There is no implicit default mode and no legacy `--mode`
option.

| Option | Meaning |
|---|---|
| `INPUT` | Combined custom-level/replay text file or libTAS `.ltm` movie. This remains positional even when TOML is used. |
| `-o FILE`, `--output FILE` | Required same-format output, except with `--list-objects`. Must differ from the input; an LTM input requires an LTM output. |
| `--levels-file FILE` | Level database for a raw LTM. Usually discovered automatically; explicitly supplying it also overrides an embedded level record. LTM-only. |
| `--level-id NN-N` | Level ID when it cannot be inferred from an LTM filename or embedded metadata. LTM-only. |
| `--ltm-postroll N` | Raw-LTM replay boundary override: treat exactly the final `N` active-input rows as padding. `0` keeps every post-Space row. LTM-only. |
| `--replay-output FILE` | Optional replay-only output. Must differ from both other paths. |
| `--config FILE` | Load defaults from a TOML file. Explicit scalar CLI options take precedence. |
| `--retime START:DELTA` | Apply a fixed-length transition-suffix retime before the selected search. Repeatable. |
| `--list-objects` | Print stable target and interaction selectors, then exit. No output or target frame is required. |
| `--workers N\|auto` | Select a positive process count. `1` always forces serial; `auto` is the default. |
| `--simulate-enemies` | Enable the supported enemy model. |
| `--no-simulate-enemies` | Disable it. Auto defaults to enabled; Local and jump-pattern default to disabled. |

Only options valid for the selected mode are accepted. For example, Local
rejects `--iterations`, jump-pattern rejects `--seed`, and Auto rejects
`--target-frame`. The removed `--non-strict-shapes` option is also rejected.

## Auto mode

Auto is a reference-guided whole-level optimiser. It starts from a verified
completed replay, tries route-level changes, and repairs the first broken jump,
contact or route-control dependency. Its search includes suffix and boundary
retimes, horizontal pulses, jump-pulse edits, trajectory splices, sparse
direction changes and bounded all-input repair.

The source replay is always retained as a candidate. A speedrun result therefore
cannot be slower than the verified source, and every result is packed, decoded
and simulated again before it is written. On an equal primary result, exit
proximity immediately before the neutral sentinel is used as a tie-break, so an
equal-time or equal-score alternate may replace the source.

### Multiple starting parents

Keep the positional replay as the primary reference/template and repeat
`--auto-parent` for additional founders:

```bash
python optimize_replay.py auto parent_A.ltm \
  --auto-parent parent_B.ltm \
  --auto-parent parent_C.ltm \
  --workers 8 \
  --auto-runs 0 \
  --output run_next.ltm
```

The same setup in TOML is:

```toml
[auto]
parents = [
    "parent_B.ltm",
    "parent_C.ltm",
]
```

All parents must carry exactly the same serialized level. Auto applies any
configured pre-search `--retime` sequence to each parent, then runs its normal
zero-iteration canonical trimming and sentinel verification on every result.
Canonical held-input duplicates are collapsed only after verification. Input
formats may be mixed, but the positional input alone supplies the combined-text
or LTM output template.

The positional replay remains the reported campaign baseline and supplies the
reference-gold mask for `--auto-require-reference-gold`; an additional founder
which already misses that mask is rejected. The best unique founder under the
selected complete-run ordering is the starting global incumbent. Round one
distributes the worker count evenly over ranked founders: eight workers give
`4+4` for two founders, `3+3+2` for three, and one search each for eight. If
there are more unique founders than workers, only the best-ranked founders
receive a round-one search.

### Speedrun and highscore objectives

`--auto-objective speedrun` is the default and minimises raw completion tick.

`--auto-objective highscore` maximises the replay's relative timer contribution:

```text
highscore value = 80 * collected gold - finish tick
```

Highscore mode may use time after the source finish to reach extra gold.
`--auto-max-extra-ticks N` sets that editable extension. When omitted, the
default is up to 80 ticks, reduced to zero when the source already has all gold.
Use `--auto-require-reference-gold` when every exact gold collected by the
verified post-retime source must remain collected. Without it, Auto may
intentionally trade a source gold for enough time saving to improve the score.
Other exit switches, locked-door switches and trapdoors are route-state signals,
not universal preservation constraints: a fully simulated completed alternate
may legitimately skip an optional control or trigger a harmless one.

### Search rounds and workers

Each worker runs one complete seeded Auto search with its own
`--iterations` budget. With multiple workers, completed searches form a small
population: the best half (rounded up) seed the next round, while idle slots may
begin one-generation-ahead speculative work.

- `--workers auto` selects up to eight available CPUs.
- `--auto-runs 1` performs one bounded round.
- `--auto-runs N` performs `N` population rounds.
- `--auto-runs 0` continues indefinitely until Ctrl+C.
- `--workers 1` uses the serial campaign path and restarts each round from the
  current winner.

The experimental `--auto-repair-beam-width 32` mode applies only to native
Cartesian direction/all-input repairs. Sparse patch evaluation, splicing,
evolutionary selection and full replay verification continue unchanged. It
ranks partial exact simulated states against the existing repair endpoint
objective, rewards already-satisfied interactions/jumps, softly prioritises
input directions toward the target, and retains at most N distinct frontier
states per mutable frame. State keys include the full native dynamic state,
required-jump flags, and whether the sequence differs from the source; there
is no approximate merge. Both modes respect `--auto-repair-local-steps`.

Additional opt-in repair controls:

- `--auto-repair-cache-entries 16` enables a bounded, worker-local exact-query
  memo. The complete replay prefix through the target frame, all search
  constraints and the level-bound session must agree before a result is
  reused. Interrupted searches are never cached, and a hit costs zero
  additional simulated ticks. This is result memoisation, **not** unsafe
  approximate state merging or a global cross-worker transposition table.
- `--auto-adaptive-repair-windows` tries successively longer input suffix
  windows (2, 4, then the configured maximum), sharing the existing per-repair
  tick budget across horizons. Both direction-only and all-input repair paths
  use this policy; a full zero-distance endpoint can terminate early.

Neither option changes ordinary repairs unless enabled. The adaptive beam
also orders available inputs by replay similarity, target direction, braking
and jump state before simulation, **without excluding any legal input**.
The heuristic beam is **not exhaustive** and can perform worse than DFS;
compare both using identical seeds and simulation budgets. Increasing width
increases the memory used for saved native states.

Rebuild the native module after switching versions (`python build_native.py`).
`build_native.py` automatically regenerates `native/_nv14_native.c` from
`native/_nv14_native.pyx` when missing or stale; the generated C is ignored by
Git. Builds are incremental by default (`python build_native.py`); use
`python build_native.py --force` for a full native rebuild or
`python build_native.py --force-cython` to regenerate the C wrapper explicitly.
The old `--no-force` option remains accepted for compatibility.

The total nominal macro budget for a bounded campaign is
`iterations * workers * auto-runs`. Local repair simulations are reported
separately and can dominate runtime.

### Recommended long campaign pattern

```bash
python optimize_replay.py auto run.txt \
  --auto-objective speedrun \
  --iterations 10000 \
  --beam 64 \
  --max-retime 3 \
  --auto-repair-local-steps 2000 \
  --auto-campaign-local-steps 20000 \
  --auto-frame-ahead-repair-multiplier 50 \
  --workers 8 \
  --auto-runs 0 \
  --seed random \
  --output run_next.txt
```

This is intentionally unbounded. Auto writes each new globally best verified
result immediately. Ctrl+C cooperatively stops the campaign, writes the best
verified result available, and exits with status 130.

If full fidelity is needed, retain the default enemy simulation. Add
`--no-simulate-enemies` only for an explicitly exploratory run whose result will
later be checked in the full model and in the game.

### Auto mutation range

`--range START:END` restricts eligible mutation seams or starts. It is not a
strict immutable-frame mask: an allowed suffix mutation can still alter later
frames beyond `END`. Auto accepts only one continuous range.

Open-ended, full and single-frame forms are accepted, for example
`--range :250`, `--range 100:`, `--range :` and `--range 175`.

### Auto tuning

- Increase `--iterations` for more proposals per independent search.
- Increase `--beam` for diversity, at greater memory and candidate-management
  cost.
- Increase `--auto-repair-local-steps` when promising edits repeatedly reach a
  broken jump or contact that the default repair cannot solve.
- Increase `--auto-campaign-local-steps` when a whole repair campaign ends
  before exploring enough alternatives.
- Increase `--auto-frame-ahead-repair-multiplier` when frame-ahead candidates
  deserve substantially deeper repair. A value of `1` disables this bonus.
- Use `--auto-no-deterministic` for repeated stochastic campaigns when the
  structured bootstrap has already been thoroughly explored.
- Keep a printed integer seed to reproduce a useful `--seed random` campaign.

Both repair ceilings count fresh local simulations. A base value of `0` means
unlimited; use it cautiously. The campaign ceiling is soft and checked between
repair attempts. Alignment tolerances guide proposals only: candidates still
receive complete simulation and final verification.

## Local mode

## Local hybrid search (opt-in)

Local **sliding-window** search (`--search windows`, the default) can now use
JaffarPlus-inspired native search improvements. For example:

```bash
python optimize_replay.py local run.txt \
  --target-frame 161 --range 100:161 --window 6 --passes 2 \
  --local-beam-width 32 \
  --local-search-cache-entries 16 \
  --local-adaptive-windows --local-search-ticks 20000 \
  --output run_hybrid.txt
```

- `--local-beam-width N` (alias `--beam-width`; range 0..4096) switches the
  native search from exhaustive DFS (0, the default) to a reward-guided beam
  (N). This automatically enables **state-aware ordering of all legal inputs**;
  it does *not* exclude unusual inputs.
- `--local-search-cache-entries N` (alias `--search-cache-entries`, range 0..64)
  memoizes exact completed queries within each independent local run, including
  their original input prefix and all constraints. Budget-exhausted searches
  are not cached. A cache does *not* approximate or merge different states.
- `--local-adaptive-windows` (alias `--adaptive-windows`) tries trailing
  subsets containing 2, 4, then the full number of mutable frames in a selected
  window (duplicate sizes are skipped). With sparse windows, subsets select
  only originally permitted mutable frames; fixed intervening frames stay fixed.
- `--local-search-ticks N` caps **native simulated ticks per selected window**.
  Adaptive horizons split this total budget, reserving a share for the final
  full-window attempt. Without adaptive windows, 0 means unlimited (the old
  behavior); with adaptive windows, 0 automatically selects 20,000 ticks per
  window to prevent accidental runaway exploration. This budget is **per
  window**, not a global campaign limit.

All changes are disabled by default, so commands without these options retain
original local DFS behavior and results. The endpoint objective, hard
constraints, jump-preservation rules, multi-worker semantics and final replay
verification are unchanged. Enable `--python-resimulate` for an extra Python
simulation parity check during local search. Match seeds, input replay and
simulation budgets for A/B comparisons; reward-guided beam does not prove
optimality.

**Scope:** these switches apply to `--search windows` (contiguous, sparse or
mixed), **not** `--search population`, which uses a different candidate
proposal/evaluation engine. Using any hybrid option with population raises a
configuration error instead of silently ignoring it. The existing `--beam`
option is unrelated: it controls the population's number of survivors.

Local search is a greedy overlapping-window optimiser, not a global exhaustive
proof over the whole range. It exhaustively searches each small frame set,
accepts a useful candidate as the incumbent for later windows, and refines the
result across passes. Window order can therefore affect the final result.

Frames after the last mutable frame are replayed unchanged through the target
frame, so delayed effects are included in scoring. `--target-frame` is required.
If `--range` is omitted, every frame from 0 through the target frame is mutable.

### Mutable ranges

Local accepts one or more inclusive ranges:

```text
--range 90:105
--range 90:105,250:280
--range :105
--range 250:
--range :
--range 90
```

Multiple intervals are sorted and overlapping or adjacent entries are merged.
With disjoint ranges:

- contiguous windows stay inside one interval and never bridge an excluded gap;
- sparse windows select from the union and may coordinate frames in different
  intervals while every gap input remains fixed;
- `--window-span` measures the real inclusive distance from the first selected
  frame to the last, including any excluded gap;
- direction-only jump mutations affect only complete source jump pulses wholly
  contained in one interval.

The range end cannot be later than the target frame.

### Input alphabets

`--local-inputs all` is the default. Each mutable frame can be Left, Neutral or
Right, crossed with jump released or held: six theoretical choices per frame.
The raw upper bound for a `W`-frame window is `6^W`, although inactive-jump,
death and duplicate-state pruning usually remove many branches.

`--local-inputs direction` searches only Left, Neutral or Right and preserves
the replay's jump-held sequence: `3^W` theoretical choices. Every rising
jump-button press through the target frame is treated as a required successful
`Player.jump()` event. If the reference contains an inactive press, Local may
repair it through horizontal changes, but it will not silently output a run
that still misses a required press.

Direction-only mode is usually the practical choice for wider windows when the
jump timing is already good.

### Window shapes

`--window N` sets the number of mutable frames searched together. The default is
4. If the requested size is larger than the available mutable set, it is
reduced to the available size.

`--window-shape` controls which frames form a window:

| Shape | Behaviour |
|---|---|
| `contiguous` | Ordinary overlapping consecutive windows. This is the default. |
| `sparse` | Randomly samples `--window` mutable frames; intervening inputs stay fixed. |
| `mixed` | Alternates sparse, contiguous, sparse, contiguous passes, starting sparse. |

For sparse passes:

- `--window-span N` limits the inclusive first-to-last frame span. It must be at
  least the effective window size. Omitting it allows the full mutable range.
- `--windows-per-pass N` controls how many distinct random frame sets are tried.
  Its default is the number of ordinary contiguous windows. Sampling cannot
  exceed the number of feasible distinct sets.

`--window-span` and `--windows-per-pass` are invalid with a purely contiguous
shape. A contiguous pass with no accepted change can stop that trajectory
early; sparse searches still sample later passes because they may select new
frame sets.

### Window order and independent trajectories

`--window-order` controls traversal:

| Order | Behaviour |
|---|---|
| `forward` | Visits windows by increasing temporal centre. Default. |
| `reverse` | Visits them in the opposite order. |
| `random` | Runs `--restarts N` independent shuffled trajectories, each starting from the untouched post-retime replay. |
| `mixed` | Compares one forward trajectory, one reverse trajectory and `--restarts N` random trajectories. |

`--window-shape mixed` and `--window-order mixed` are independent controls. The
first mixes sparse and contiguous passes inside a trajectory; the second mixes
different trajectory orders.

Use an integer `--seed N` to reproduce sparse sampling or random/mixed order.
When randomness is needed and no seed is supplied, Local generates and prints a
seed. The literal `--seed random` is Auto-only and is rejected by Local.

### Direction-only jump mutation

Random or mixed direction-only searches can vary complete source jump pulses
before each random restart:

```bash
python optimize_replay.py local run.txt \
  --target-frame 300 \
  --range 120:300 \
  --objective max-x \
  --local-inputs direction \
  --window-order mixed \
  --restarts 20 \
  --jump-start-mutation 2 \
  --jump-length-mutation 3 \
  --immutable-jumps 142:both,210:start,245:length \
  --output run_optimised.txt
```

- `--jump-start-mutation X` samples each eligible start offset in `[-X,+X]`.
- `--jump-length-mutation Y` samples each eligible hold-length offset in
  `[-Y,+Y]`, keeping length at least one and valid released gaps between pulses.
- `--immutable-jumps FRAME[:PROPERTY],...` preserves `start`, `length` or
  `both` for named post-retime source pulses. A bare frame means `both`.

Jump mutation requires `--local-inputs direction`, a `random` or `mixed` window
order, and at least one non-zero mutation bound. An unmutated control trajectory
is retained so enabling mutation cannot discard the original jump timing.

### Optional physics pruning

`--physics-prune` enables a horizontal kinematic branch-and-bound in
direction-only mode. It is safe only when the future path cannot acquire a
horizontal boost from an object or collision. Launch pads, bounce blocks,
thwomps and unusual collision boosts can violate that assumption. Leave it off
unless the searched section is understood. It principally helps `max-x`,
`min-x` and searches with an x window.

### Local constraints and checkpoints

Local can require or prohibit persistent route interactions; see
[Required and forbidden interactions](#required-and-forbidden-interactions).
Hard interaction repairs and required successful jump presses outrank the
positional objective. `--minimum-improvement D` applies only to ordinary
positional gains; use a non-negative value in normal searches.

Every accepted candidate that becomes the best checkpoint so far is packed,
decoded, simulated from frame zero and checked against all hard constraints
before it replaces the output. This protects useful progress during long serial
or multi-worker searches.

## Jump-pattern mode

Jump-pattern is specialised for a route whose horizontal inputs are already
useful but whose jump timing needs exhaustive search.

Inside one continuous `--range`, it replaces only the jump-held stream with
non-overlapping pulses represented by `start frame + hold length`. Left/right
input is preserved frame-for-frame, and inputs outside the range are unchanged.
At least `--minimum-gap` released frames separate pulses.

A pulse counts toward `--jumps` only when its rising edge actually invokes
`Player.jump()` in the emulated state. Inactive airborne button presses are
discarded rather than counted as jumps.

### Jump counts and lengths

```text
--jumps 2        exactly two successful jumps
--jumps 2:4      two, three or four successful jumps
--jump-length 5  exactly five held frames per pulse
--jump-length 2:10
--jump-length 2: maximum length that fits
```

Defaults are `--jumps 2:3`, `--jump-length 1:`, `--minimum-gap 1` and
`--top-results 10`.

The optimiser prints the retained ranked patterns and writes the best one.
Frames after the mutable range are simulated unchanged through
`--target-frame`, so the objective can measure a delayed landing or boost.

### Fixed jump starts

`--fixed-jump-frames F1,F2,...` requires selected rising edges in the
post-retime source to remain at exactly those frames while still searching
their hold lengths. Movable pulses may appear before, between or after them.

Each fixed frame must:

- lie inside the jump-pattern range;
- be a jump rising edge in the source replay;
- permit a physically successful jump in every retained branch;
- fit the configured jump-count, hold-length and minimum-gap constraints.

Jump-pattern has no random seed. Its search is exhaustive over physically
distinct reachable states within the requested pulse bounds. Multiple workers
partition exact frontier states; tied retained ordering can differ between
serial and parallel runs, but ranking and state verification remain exact.

Jump-pattern does not support disjoint ranges or Local interaction constraints.
Its search space grows combinatorially, so narrowing the range, jump count and
maximum hold length—or fixing known starts—has the largest effect on runtime.

## Objectives, targets and coordinate constraints

Local and jump-pattern share these target-frame objectives:

| Objective | Meaning |
|---|---|
| `max-x` | Move as far right as possible. |
| `min-x` | Move as far left as possible. |
| `max-y` | Maximise y; n's screen coordinates increase downward. |
| `min-y` | Minimise y; move upward. |
| `min-distance` | Minimise Euclidean distance from the player's centre to a point or object anchor. |

`min-distance` requires exactly one of:

```text
--target-point X,Y
--target-object SELECTOR
```

### Object selectors

List a level's stable selectors and coordinates before choosing one:

```bash
python optimize_replay.py local run.txt --list-objects
```

Selectors use stable per-type indices in level-data order:

```text
TYPE
TYPE:INDEX
TYPE:any
TYPE:INDEX.ANCHOR
TYPE:any.ANCHOR
```

Examples:

```text
exit                 one unambiguous exit; defaults to its door
exit:0.door          first exit's door
exit:1.switch        second exit's switch
exit:any.door        nearest exit door
switch:1             switch belonging to exit:1
gold:7               eighth gold
gold:any             nearest gold
bounceblock:0        first bounce block's centre
```

A bare type is accepted only when exactly one matching object exists. Use an
explicit index to choose an identity or `:any` to target the nearest matching
object. Exits expose `.door` and `.switch`; most point-like types expose
`.center`. Supported target types are `gold`, `bounceblock`, `launchpad`,
`turret`, `floorguard`, `player`, `drone`, `onewayplatform`, `thwomp`,
`testdoor`, `hominglauncher`, `exit`, `mine`, plus the `switch` pseudo-type.
`--list-objects` is authoritative for the level.

### Coordinate windows

`--x-window` and `--y-window` are inclusive hard constraints at the target
frame. They can accompany any Local or jump-pattern objective:

```bash
python optimize_replay.py local run.txt \
  --target-frame 161 \
  --range 100:161 \
  --objective max-x \
  --y-window 98.7:98.9 \
  --window 4 \
  --passes 3 \
  --output run_optimised.txt
```

Accepted forms include:

```text
--x-window 500:700
--x-window :700
--x-window 500:
--x-window 600
```

A single value requests exact binary64 equality. A narrow interval is usually
more practical than exact floating-point equality. Candidates that die or fall
outside either coordinate window are infeasible.

## Required and forbidden interactions

These controls are Local-only and are checked through the target frame,
including immutable prefixes, excluded range gaps and unchanged suffixes.
Repeat an option to combine several conditions with AND.

### Requirements

```bash
python optimize_replay.py local run.txt \
  --target-frame 400 \
  --range 200:400 \
  --objective max-x \
  --require-interaction gold:7 \
  --require-interaction switch:0 \
  --require-interaction testdoor:2 \
  --window 6 \
  --passes 3 \
  --output run_optimised.txt
```

Supported positive requirements are:

| Selector | Requirement |
|---|---|
| `gold:INDEX`, `gold:any` | Collect the exact gold, or at least one gold. |
| `switch:INDEX`, `switch:any` | Activate the exact exit switch, or at least one. |
| `exit:INDEX.switch` | Alias for the corresponding `switch:INDEX`. |
| `testdoor:INDEX`, `testdoor:any` | Activate the exact locked TestDoor switch, or at least one locked-door switch. |

Bare `gold`, `switch` and locked `testdoor` selectors are also accepted when
exactly one valid matching interaction exists.

`--require-reference-interactions` derives exact requirements for every gold,
exit switch and locked-door switch used by the post-retime reference replay
through the target frame. It preserves identities, not merely counts.

### Avoidances

Supported persistent avoidances are:

| Selector | Prohibition |
|---|---|
| `gold:INDEX`, `gold:any` | Do not collect that gold, or any gold. |
| `switch:INDEX`, `switch:any` | Do not activate that exit switch, or any exit switch. |
| `exit:INDEX.switch` | Alias for the corresponding switch. |
| `testdoor:INDEX`, `testdoor:any` | Do not activate that persistent locked-door or trapdoor interaction, or any such TestDoor. |
| `trapdoor:INDEX`, `trapdoor:any` | Do not trigger that trapdoor, or any trapdoor. The index is the stable **testdoor** index. |

Bare avoidance types are accepted only when exactly one valid persistent match
exists.

For a requirement, `TYPE:any` means at least one matching object satisfies the
condition. For an avoidance, it means every matching object is forbidden.

Ordinary proximity doors are not valid persistent interaction constraints: they
can close again, so target-frame state does not prove whether they were touched.
Trapdoors can be forbidden because triggering one leaves persistent state, but
they cannot be positive requirements.

An explicit requirement may ask Local to repair an interaction absent from the
source. A forbidden interaction already present in the source may likewise be
repaired. The search will not exchange one exact missing or violated identity
for a different one merely to improve position. For a distant new interaction,
it is often effective to minimise distance to it first, then enforce it as a
hard requirement in a later pass.

## Replay retiming

Every mode accepts repeatable pre-search retimes:

```text
--retime START:DELTA
--retime whole:DELTA
```

`DELTA` must be `-3`, `-2`, `-1`, `+1`, `+2` or `+3`.

`START` must be an actual held-input transition frame. Transitions compare the
Left/Right/Jump-held tuple with the preceding frame; jump-trigger bits are
ignored. Frame zero is a transition only when the replay begins non-neutral.
`whole` selects the first current transition.

Every transition at `START` and later moves by the same delta while total replay
length remains fixed. A negative delta advances the suffix; a positive delta
delays it. A retime is rejected if it would overtake the preceding transition,
move before frame zero, or push a transition beyond the replay end.

Repeated specs are applied sequentially, so later `START` values are validated
against the already-retimed replay:

```bash
python optimize_replay.py local run.txt \
  --retime whole:-1 \
  --retime 120:+1 \
  --target-frame 300 \
  --range 200:300 \
  --objective max-x \
  --output run_optimised.txt
```

In Local, the original source is printed as the baseline and the retimed replay
is the search seed. Reference-derived interactions come from the post-retime
seed. In Auto, the retimed replay is the route that must pass source completion
verification and from which reference gold is derived.

## TOML configuration

Use `--config FILE` to provide defaults while keeping the mode and input
positional:

```bash
python optimize_replay.py local run.txt \
  --config examples/config/local.toml \
  --output run_optimised.txt
```

TOML may contain legacy top-level option keys, a `[common]` table and separate
mode tables. Only the selected mode table is applied; other known mode tables
may coexist for later runs.

```toml
[common]
workers = 8
simulate_enemies = false
replay_output = "run_optimised.replay"

[local]
target_frame = 300
range = ["90:105", "250:280"]
objective = "min-distance"
target_object = "exit:0.door"
window = 6
window_shape = "mixed"
window_span = 96
windows_per_pass = 50
window_order = "mixed"
restarts = 10
seed = 123456
require_interaction = ["switch:0", "testdoor:1"]
avoid_interaction = ["trapdoor:any"]
```

LTM resolution and output paths are also ordinary common options. For example:

```toml
[common]
levels_file = "external/N v1.4 + NReality levels.txt"
level_id = "00-0"
ltm_postroll = 3
output = "recording_optimised.ltm"
replay_output = "recording_optimised.replay"
```

`levels_file`, `level_id` and `ltm_postroll` are rejected when `INPUT` is not an
LTM. `ltm_postroll` is normally needed only for the first pass over an ambiguous
raw movie; remove it on later passes to use the exact embedded tick count.
The level options can normally be omitted after the first v2.70 pass because
the output movie embeds the exact level record and identifier.

Rules:

- Effective precedence is built-in defaults, top-level keys, `[common]`, the
  selected mode table, then explicit CLI scalar options.
- Repeatable CLI options (`retime`, `require_interaction` and
  `avoid_interaction`) append to configured arrays rather than replacing them.
- A CLI `--range` is scalar and replaces a Local TOML range array.
- Keys may use underscores or CLI-style hyphens.
- In a mode table, the mode prefix may be omitted: `objective` under `[auto]`
  means `auto_objective`, and `runs` means `auto_runs`.
- `[jump_pattern]` is accepted as an alias for `[jump-pattern]`, but do not
  define both.
- The mode, input and config path cannot themselves be supplied by TOML.
  `output`, `replay_output`, `levels_file`, `level_id` and `ltm_postroll` may be
  supplied.
- Unknown sections, unknown keys, invalid types and settings belonging to
  another mode are errors rather than silently ignored.
- Put only genuinely shared settings in `[common]`; an Auto-only key there will
  make the same file invalid when selected with Local or jump-pattern.
- TOML paths are resolved relative to the process working directory, not the
  config file's directory.
- `workers` is either the string `"auto"` or a positive integer; numeric zero is
  not an accepted CLI/TOML spelling.

Convenient arrays are supported:

```toml
[common]
retime = ["whole:-1", "120:+1"]

[local]
target_point = [470.0, 432.0]
x_window = [0.0, 500.0]
range = ["90:105", "250:280"]
immutable_jumps = ["42:both", "73:start"]

[jump-pattern]
jumps = [2, 3]
jump_length = [1, 8]
fixed_jump_frames = [42, 73]
```

TOML has no null value. Use strings for open-ended values, such as
`x_window = ":500"` or `jump_length = "1:"`.

Boolean destination names are often the clearest TOML spelling:

```toml
[auto]
deterministic = false
all_input_repair = false
require_reference_gold = true
```


## Seeds, workers, checkpoints and interruption

### Seeds

- Auto defaults to deterministic seed `0`.
- Auto accepts an integer or `--seed random`; the latter chooses and prints one
  fresh 64-bit master seed.
- Local accepts an integer seed. When a sparse or random/mixed search needs a
  seed and none is supplied, it generates and prints one.
- Jump-pattern is exhaustive and has no seed option.

Worker seeds are deterministically derived from the master seed and worker
tasks. Keep the printed master seed and the same configuration to reproduce a
campaign.

### Workers

`--workers auto` is mode-aware:

- Auto uses up to eight independent CPU-bound searches per round.
- Jump-pattern adapts to the number and cost of independent frontier branches,
  up to eight available CPUs.
- Local first parallelises independent forward/reverse/random trajectories. A
  lone sufficiently expensive trajectory may instead split a safe DFS frontier
  within its current window. Small searches may deliberately remain serial.

`--workers 1` is the reliable low-overhead choice for tiny searches and exact
performance comparisons. Multiprocessing is supported on Windows, macOS and
Linux.

### Checkpoints and Ctrl+C

- Auto checkpoints every new global verified best. On Ctrl+C it retains and
  writes the best verified result, then exits with status 130.
- Local checkpoints new best candidates from the parent process after clean
  frame-zero verification. If interrupted, the latest completed checkpoint
  remains on disk, though a run interrupted before its first improvement may
  not yet have created output.
- Jump-pattern writes only after the exhaustive search finds and verifies a
  feasible winner; interrupting it before completion normally produces no new
  output.

The same checkpoint rules apply to LTM runs. Every accepted Auto or Local
checkpoint is rebuilt atomically from the original movie template, with its
exact replay/level metadata refreshed; `--replay-output`, when requested, is
updated to the same packed replay.

All multiprocessing workers leave Ctrl+C handling to the parent process to
avoid competing writes or noisy child tracebacks.

## Emulation scope and fidelity

Static and core physics are always enabled. The emulator includes the parts of
n v1.4 used by the bundled search and regression corpus, including:

- Player Verlet integration and standing, running, skidding, jumping, falling
  and wall-sliding states.
- Source-order object, thinker, player, object-collision and tile-collision
  processing.
- All standard static tile shapes (IDs 0–33), including slopes, curved tiles and
  half tiles.
- One-way platforms, launch pads, bounce blocks and thwomps.
- Gold, mines, exits and exit switches.
- Locked, proximity and trap `TestDoor` behaviour.
- Optional floorguards, zap/laser/chaingun drones, homing launchers and gauss
  turrets.
- Mutable object state cloning, ordering and branch isolation.

The enemy toggle controls only the supported optional enemies listed above;
thwomps and the static/interactive objects remain simulated.

| Mode | Enemy default |
|---|---|
| Auto | Enabled, because whole-route completion should use the fuller model. |
| Local | Disabled, for cheaper targeted searches unless explicitly requested. |
| Jump-pattern | Disabled for the same reason. |

Choose the same enemy setting used to create or verify the source trace. A
result found with enemies disabled is valid only in that reduced model until it
is checked again with enemies enabled and in n v1.4.

Intentionally omitted are unlisted enemy/object behaviours, presentation-only
sound/animation/GUI behaviour, death-ragdoll simulation after a terminal
branch, and the episode countdown time-out system. Unknown static tile shapes
are errors.

Final packed output is always decoded and simulated cleanly from frame zero in
the selected model. This detects serialization differences, deaths, hard
constraint failures and state mismatches before a result is accepted.

### Auto with Local-compatible endpoint goals

`auto` now accepts the same position, distance, earliest-arrival, and

`[auto]` and `[local]` search budgets. Auto endpoint searches allow partial
replays by default; set `completion-policy = "complete"` under `[auto]` to
require a verified level finish. The existing speedrun/highscore Auto engine
is unchanged. See [Auto endpoint objectives](docs/AUTO_ENDPOINT_OBJECTIVES.md)
and [shared example config](examples/config/shared-endpoint.toml).

**Multiple required jumps in a Local/Auto splice objective:** see
`examples/config/local-multiple-jumps.toml` and
`docs/AUTO_ENDPOINT_OBJECTIVES.md`. Both `local --config` and Auto
`--goal-config` can use the same `[[local.require-jumps]]` TOML entries.

### Switch-safe random waypoint splicing

For micro-optimising a **completed** Auto speedrun, `auto --auto-random-splice`
creates random spatial waypoints along the best replay and reuses Local
population search for earlier arrivals and progressive seam repairs. It
hard-preserves reference switch/door/trapdoor interactions and verifies
completed replays before saving: shorter finishes always win, while at an
equal frame count the closer pre-finish exit approach wins. Waypoint count or distance, region
radius, lookback, Local budget and repair depth are configurable under `[auto]`
or as CLI arguments. Use `splice-frames-per-point = 100` to scale the number
of checkpoints with run length; `splice-mode = "complexity"` targets boundaries
of rapid input sequences, and `splice-mode = "physics"` targets switches,
walljumps, and landings (with optional bounce-block events). See
[docs/RANDOM_SPLICE.md](docs/RANDOM_SPLICE.md).

### User-defined multi-splicing (ordered Local splice files)

The Python multi-splicer runs inside `auto` and reuses the existing random
splicer's Local-population or endpoint-Auto search backends. Unlike random,
complexity, or physics waypoints, its checkpoints are **explicit Local goal
files**, attempted in exactly the order listed. For level `97-2`, add:

```toml
[auto]
splice-files = ["203", "408", "switch", "end"]
runs = 5
splice-iterations = 400
splice-rounds = 1
splice-frontier = 3
```

This is sufficient to select `random-splice = true` and `splice-mode = "user"`
automatically.

To **share all multi-splicer settings between levels**, keep a reusable
`[multi-splicer]` section in `examples/config.toml` alongside your regular
`[auto]` and `[common]` settings:

```toml
# examples/config.toml
[multi-splicer]
search = "both"
iterations = 400    # proposals per worker, per stage seed, per internal round
rounds = 3         # internal rounds per stage seed
frontier = 3
runs = 5           # complete passes through the named splices
```

Then each level's file needs only the ordered splice names:

```toml
# ../splices/97-2/multi-splicer.toml
[multi-splicer]
# Route-scale Auto mutation presets: low (default), medium, high, or an array
# naming only selected operators (see examples/config.toml for explanations).
mutations = "low"
files = ["203", "408", "switch", "end"]
# Optional: allow the next splice to reuse seeds from n-1, n-2, n-3, etc.
lookback = 3
save-frontier = 64          # persist alternatives; does NOT increase search seeds
# Multi-worker splicing coalesces live best updates (up to ~30 s per worker)
# and saves the diverse frontier at stage boundaries. This avoids serial
# validation and disk writes stalling active search workers. Backend round
# checkpoints still protect completed rounds from Ctrl+C.
# `frontier = 3` in the shared configuration still controls actual searches.
```

`mutations` enables additional route-scale operators in endpoint Auto only (not
Local). `low` uses long `direction-flip`, short neutral `gap-repair`, and
`direction-simplify` (removing brief reversals); `medium` adds large
`boundary-shift`, jump-pulse `jump-rewrite`, and between-jumps
`passage-rewrite`. `high` also uses physics-aware `state-crossover`
between candidates with similar position and velocity at the seam. The
structural operators now scan compact inputs in the Cython native module,
and crossover compares native replay traces rather than repeatedly invoking
Python physics. Rebuild with `python build_native.py` after applying this patch.
The Python reference remains available when the native extension is absent. An explicit
TOML array such as `mutations = ["direction-flip", "gap-repair"]` uses exactly
those operators; `mutations = []` disables all new route-scale edits for
an A/B comparison against the previous Hybrid behavior. These proposals
consume part of Auto's existing evaluation budget (roughly 10%/20%/30% in
low/medium/high); their usefulness should be
benchmarked at equal evaluation count, since broad edits often fail. CLI:
`--auto-mutations high` or `--auto-mutations direction-flip,gap-repair`.

`lookback` is the **number of preceding splice frontiers**, not a count of
skipped stages: `2` (default) keeps the previous n-1/n-2 behavior; `3`
includes n-3, and `1` only uses n-1. This is independent of the existing
`--auto-splice-lookback` frame-mutation setting. The existing n-1/n-2 seeds stay unchanged; one additional distinct seed
from each older frontier is appended. Extra historical seeds increase the
search budget because each seed runs its own backend search. Put `lookback` in the
per-level file when different levels need different amounts of bypassing.
To inspect **only the saved splice propagation summary** without searching or
writing checkpoints, use `-l` or `--ls-splice` with the normal `auto` command,
`--splice-config`, `--output`, and (if used for checkpoint names) `--replay-output`.
The report lists each named stage as pending, propagated, or missing, compares
its best saved checkpoint with the saved final replay, and exits. When the
final output file is absent, the input replay serves as the comparison baseline.
`--output` is required to locate the checkpoint filenames; no file is created.

Interrupted named multi-splicer runs now retain a small validated **frontier
archive** beside each stage's best LTM/TXT, named `optim_STAGE.frontier.json`
(or the corresponding `--output` stem). Archives are atomically rewritten with
the top `frontier` distinct stage-feasible candidates, checked against the
level and stage settings on the next run. The old best stage LTM/TXT files
remain compatible and serve as fallback seeds when no archive exists.
`--splice-from-best STAGE` starts from that saved best and additionally
restores the preceding n-2, n-3, etc. frontiers up to `lookback`; a normal
restart also reuses saved frontiers. Each completed stage saves its updated
frontier, and a newly discovered stage best updates the archive immediately,
so Ctrl+C may discard only the live backend population/current unfinished
search. An existing `--output` replay is independently verified and used as
the final-score baseline, preventing a restart with an older input from
overwriting a better completed replay. Changed or invalid existing final
outputs cannot veto a new campaign; only verified improvements replace a
previously verified completed output. `--ls-splices` remains read-only.

Set `save-frontier = 64` in either the shared or per-level `[multi-splicer]`
configuration (default 64; maximum 256). Unlike `frontier`, which controls
how many routes are *searched*, `save-frontier` only limits the on-disk
`.frontier.json` archive. Saved candidates are reverified on restore; a mix
of strong scores and physically different endpoint position/velocity niches
is retained. The CLI equivalent is `--splice-save-frontier 64`.

For named splices using independent Auto/Local stagnation limits, the current
backend additionally saves a round-boundary checkpoint after every completed
backend round, with a previous-round `.prev` backup. Auto retains its verified
best and inherited population; Local retains its candidate population and
its round/evaluation/stagnation counters. A small `.splice-search.json`
sidecar beside the final `--output` remembers the interrupted splice, backend,
source seed, outer pass and random state. Re-running the **same** command
resumes the last completed backend round if that state remains compatible.
The physics level, goals, search settings, input and code build must match.
Use a different `--output` directory for an independent search. Ctrl+C in the
middle of a round discards only that partial round. Once a phase completes,
its next phase starts with a fresh backend checkpoint. The sidecar is removed
after an interrupted phase finally completes; normal completed runs do not
retain a pointer to an active phase. `--ls-splices` remains read-only.

The CLI equivalent is `--splice-stage-lookback 3`.

Options from the two `[multi-splicer]` tables merge by key: the level file
can optionally override individual shared options without resetting the others.
The shared `[multi-splicer]` table is dormant for ordinary Auto runs if no
named splice list is selected, so it does not override regular `[auto] runs`
or other Auto settings. Both formats continue to work when everything is
specified in a single file.

Run from the `optimiser/` directory:

```sh
python3 optimize_replay.py auto ../n_levels/97-2.ltm \
  --config examples/config.toml \
  --splice-config ../splices/97-2/multi-splicer.toml \
  --output wip/optim.ltm --replay-output wip/97-2.txt --workers 15
```

To **merge saved splice bests once and exit**, use the same command with
`--splice-merge-only`. It implies `--splice-merge-bests` and tests
replay-verified joins from **all** earlier saved splice LTM/TXT checkpoints.
**The positional input replay is tried first**, before saved-stage-to-stage
pairs, even when a manual change leaves it unable to reach a later helper goal.
The older **verified saved completed output** is a separate suffix candidate,
not a replacement for that input. Input-to-saved joins must include at least
its first changed input frame, so a seam before the edit cannot silently
reproduce the old route. A truncated input with no changed input presses can
still reconnect to its saved continuation. The merge tests
seams at named splice boundaries and at the input's last live frame, so a
partial manual route can sometimes reconnect to the previous completed route.
It prints the exact input and saved-output paths to prevent editing the wrong
replay: in the example below, edit `../n_levels/88-4.ltm` or use the actual
edited file as the positional argument. Editing only `wip/88-4.ltm` does **not**
change that input. This behavior also applies to startup and final merge passes
under `merge-bests = true`.

Merge pairing is independent of `--splice-stage-lookback` (default 2), which
still controls ordinary search frontier seeds. Besides the stage-best checkpoint,
fast merge considers **one independent archived candidate per stage** in both
prefix and suffix roles. It prioritizes the fastest measured section when the
goals permit measuring actual elapsed section time; otherwise it uses an archived
alternative without claiming it is faster. A later-arriving but locally faster
section is not discarded simply because its absolute arrival is worse. A
failed splice pair (e.g. 564) never prevents attempting other pairs (e.g. 522 ->
614). This adds some verified seam attempts, but no mutation/repair searches.
The summary reports current-input and archived-alternative graft attempts
separately. Only independently verified completed improvements replace the final
output; stage-feasible grafts may update their own checkpoints/frontiers.
A manually edited input that already completes faster than the saved output is
also written immediately in merge-only mode after independent verification.
An incomplete stage graft is **never** promoted to a completed best.

**This is still a direct verified suffix graft, not an Auto/Local bridge-repair
search:** if no physically compatible join exists, merge-only reports rejection
and keeps the original completed best. Increasing search lookback is not necessary
for choosing all earlier stages; seam lookback affects only nearby join attempts.
No Auto/Local search, startup baseline checkpoint writes, or search
resume/progress sidecar changes occur. `--auto-runs` and `--workers` do not
govern this one-shot operation.

For example, starting in `optimiser/`:

```sh
python3 optimize_replay.py auto ../n_levels/88-4.ltm \
  --config examples/config.toml \
  --splice-config ../splices/88-4/multi-splicer.toml \
  --output wip/88-4.ltm --replay-output wip/88-4.txt \
  --splice-merge-only
```

With `--splice-merge-bests` (or `[multi-splicer] merge-bests = true`),
the exact same verified direct-join pass runs **twice**: once before the normal
Auto/Local searches, and again after the search finishes. The final pass uses
stage bests saved during that campaign, so it can immediately propagate a
new discovery. `--splice-merge-only` stays one pass and exits without search.
No separate search-lookback increase or additional option is required; the
seam search still uses the existing `--auto-splice-lookback` (default 32 frames).
These merge passes do not perform input-mutation bridge repairs: the
`--auto-endpoint-repair-steps` setting applies inside the endpoint Auto search,
not to merging incompatible replay suffixes.

### Bounded bridge repair for saved splice and manual-input gains

**Patch 52 adds a separate, opt-in Auto/Local repair mode.** Existing
`--splice-merge-only` remains the fast, mutation-free direct-graft operation.
When a direct join fails, `--splice-merge-repair-only` runs the fast merge first,
then tries to mutate a short bridge in the *earlier* replay toward a physical
state on a saved later-stage route or verified saved completed run. It uses the
existing endpoint Auto/Local search engine; it does **not** reuse or depend on
`endpoint-repair-steps`, which repairs proposals *within* ordinary endpoint
searches and may be inactive with progressive refinement.

Use the same input/output/splice arguments as `--splice-merge-only`, replacing
that flag with:

```sh
--splice-merge-repair-only --splice-merge-repair-pairs 48
```

A manually edited run must still be supplied as the positional input. Standalone
repair **does not run the normal named-stage optimisation campaign**, create
initial checkpoints, or alter the search-resume sidecars. Only independently
replayed, verified completed improvements replace the final output; feasible
partial grafts may update their own saved splice frontier and best checkpoint.

To run bounded repair **after** a normal multi-splicer campaign instead, put:

```toml
[multi-splicer]
merge-repair-at-end = true
# Optional effort controls; do not change normal stage seed lookback:
merge-repair-pairs = 48
merge-repair-window = 48
merge-repair-targets = 2
repair-iterations = 250
```

The CLI equivalent is `--splice-merge-repair-at-end`, which implies
`--splice-merge-bests`; a normal run still performs fast startup and final
merges. Repair occurs **only at the end**, after the final fast merge, and is
skipped on Ctrl+C. An explicit standalone `--splice-merge-repair-only` overrides a reusable
`repair-at-end = true` TOML setting for that invocation.

- `merge-repair-pairs` caps independent source/suffix pairs across the entire
  pass, including unsuccessful pairs. A failed route never blocks another.
  The positional current input retains its first opportunity by default.
  Subsequent attempts **prioritise saved earliest-arrival checkpoints with
  measured frame leads over the verified completed baseline**, giving each
  high-value source more than one continuation early (for example 527 ->
  completed and 527 -> 599). Less-promising stages and independent archived
  sections remain eligible under the remaining budget. No assumed time gain
  is assigned to spatial-only objectives or infeasible checkpoints.
- **Gain-aware suffix retiming (patch 87):** add `--retime-gains` (long form
  `--splice-merge-retime-gains`) to try deterministic input-continuation
  advances derived from **measured earliest-arrival savings** at saved splice
  checkpoints. By default, it sweeps all eligible saved stages, trying their
  saved completed continuations and the nearest later saved checkpoint; use
  `--from 777 --to completed` to restrict the pass. Each trial preserves the
  saved input prefix through the actual checkpoint arrival and appends the
  reference's later held input sequence advanced by the measured gain, plus
  small nearby offsets (0, -1, +1, -2, +2 frames). Stage/complete results are
  accepted only through existing replay, route-control and objective gates.
  `--retime-gains` alone performs **direct grafting + retiming and exits**,
  without stochastic bridge search. `--repair --retime-gains` also runs the
  normal bridge mutation search **after** retiming; its `repair-pairs` and
  `repair-iterations` budgets are independent of the deterministic sweep.
  `[multi-splicer] merge-retime-gains = true` is equivalent. `--at` is a
  *bridge mutation* seam selector and does not move the retiming boundary,
  which is the measured goal arrival. Only already-saved trajectories can be
  retimed; spatial-only goals and non-positive/unavailable savings are skipped.
  A retime is a hypothesis, **not** proof of a valid join or SWF-equivalent
  simulation. The run logs attempted and feasible trials separately from
  actual saved improvements, and never overwrites a completed best with an
  unverified replay. The sweep can be retried after saving new splices.
- Short CLI aliases (patch 85): `--merge` for `--splice-merge-only`,
  `--repair` for `--splice-merge-repair-only`, `--from NAME` for
  `--splice-merge-repair-from NAME`, and `--to NAME` for
  `--splice-merge-repair-to NAME`. All long forms and TOML keys remain valid.
  For example: `--repair --from 527 --to 599`. These are command-line flags,
  not aliases for the `tas.py merge` / `tas.py repair` positional modes.
- To restrict the **mutation-based bridge repair** to a specific source and
  destination, use `--splice-merge-repair-from 527 --splice-merge-repair-to 599`
  (TOML: `merge-repair-from = "527"`, `merge-repair-to = "599"`). The aliases
  `--splice-merge-repair-source` and `--splice-merge-repair-destination` also
  work. The source `current` means the positional input; the destination
  `completed` means any distinct verified completed suffix. A single filter
  may be supplied alone. A named stage source also includes its independently
  archived section when available. Direct mutation-free verified grafting
  still runs across all pairs; these filters only limit bridge mutation work.
  If a requested name does not exist on an alternate branch, that branch
  reports zero matching mutation pairs instead of silently repairing others.
- To **centre a bridge repair near a particular replay frame**, use
  `--merge-repair-at-frame 800` (alias `--at 800`, also accepts
  `--splice-merge-repair-at-frame 800`) or `[multi-splicer]
  merge-repair-at-frame = 800`. This is a frame in the **source replay**, not
  the destination stage name or an exact reference-tick match. Repair samples
  a small neighbourhood (at most 16 ticks either side) around that frame;
  `merge-repair-targets` still caps chosen anchors, and `merge-repair-window`
  bounds editable inputs and reference-tick exploration. The selected centre
  must be after the protected saved checkpoint and within the source replay's
  live portion. Invalid centres report a reason and do **not** silently
  fall back to the nominal stage boundary. Direct mutation-free grafting is
  unaffected. For example: `--repair --from 527 --to completed --at 800`.
- `merge-repair-window` bounds mutable inputs near the bridge, independent
  of ordinary stage history lookback. For an earliest-arrival source, the
  actual saved checkpoint arrival is a hard lower bound: the bridge cannot
  change inputs through that frame, or graft the suffix before that checkpoint.
  Live target ticks are sampled across the subsequent corridor instead of
  only three ticks near the nominal stage deadline. Physical proximity still
  guides the search, but reference states requiring lost frames are penalised.
- `merge-repair-targets` limits distinct physical target ticks per pair.
  `repair-iterations` is split across the selected bounded backend phases per
  target. In bridge repair, `search = "hybrid"` runs one endpoint-Auto phase
  followed by one Local phase *sharing candidate replays*, while the two
  Hybrid restart controls use the same phases without population handoff.
  This deliberately bounded bridge schedule does **not** run the full normal
  `hybrid-cycles` / `hybrid-local-rounds` campaign. It avoids unsupported
  Hybrid dispatch in the low-level search. `--splice-merge-verbose` reports
  individual target-pair outcomes, including whether a verified graft merely
  remains feasible or genuinely improves a stage or completion. The compact
  final report separates these categories and aggregates rejection reasons.

Example for the 527 corridor, with a larger target window if needed:

```sh
python3 optimize_replay.py auto ../n_levels/81-1.ltm \
  --splice-config ../splices/81-1/multi-splicer.toml \
  --splice-merge-repair-only \
  --splice-merge-repair-from 527 --splice-merge-repair-to 599 \
  --splice-merge-repair-pairs 16 --splice-merge-repair-targets 4 \
  --splice-merge-repair-window 64 --splice-merge-verbose
```

A repair succeeds only if both the bridge and attached suffix pass native
replay verification, canonical completion checks for a final result, and
persistent route-control preservation. **Repair is best effort:** it cannot
promise to connect every locally faster route, and does not erase a saved
checkpoint or overwrite a verified completed output after an unsuccessful
attempt. It prints separately counted feasible pairs, verified graft candidates,
actual stage and completed improvements, and search/validation failures.

Stage checkpoint summaries additionally report **section frames** between
neighboring helpers when at least one endpoint measures an actual earliest
arrival or interaction and *both* goals are feasible in that same replay.
A fastest such interval candidate gets an independent slot in the existing
saved frontier archive (when its capacity is at least two), so it remains
available as a repair prefix even when its *whole-route stage score* is
lower-ranked. Spatial-only fixed-frame goals have no measured section time;
no timing saving is inferred for them. These archived candidates remain full
replays, not disconnected input snippets, so physics is never assumed to carry
across a discontinuous section.

To keep the one-shot behavior in a splice TOML, put `merge-only = true` under
`[multi-splicer]` (or use `--splice-merge-only` on the command line).
In contrast, `merge-retime-gains = true` in TOML enables deterministic
retiming alongside **normal named-splice searching**; it does not select
standalone merge-only mode. Use `--retime-gains` on the CLI to run the
standalone retiming sweep. `merge-bests = true` and `merge-repair-at-end = true`
also retain their normal-search behaviour.
`--ls-splice` is the separate read-only summary command: unlike merge-only,
it never attempts or saves joins. Standalone merge-only uses all saved
named splice bests. A stage selection (`--start-at-splice` / `--splice-start`,
`--splice-stop`, `--splice-from-best`, or `--splice-reference`) instead starts
normal splice optimisation for the selected stages, even when standalone
`merge-only`, `merge-repair-only`, or `merge-retime-gains` is enabled in TOML.
The same precedence applies if both switches are explicitly passed on the CLI;
use `--splice-merge-bests` to request merges during normal stage optimisation.

`--splice-config` overlays all preceding `--config` files; explicit CLI
options win regardless of argument order. Splice goals are resolved relative
to the `--splice-config` file's directory by default; an explicit
`splice-directory` in the TOML or `--auto-splice-directory` on the CLI wins.
The standard `[auto]` table in existing `multi-splicer.toml` files remains
supported. `[multi-splicer]` may also appear in an ordinary `--config` file,
and does not affect Local or other modes. Within this special table, short
names (`files`, `search`, `iterations`, `rounds`, `frontier`, `lookback`,
`directory`, `start`, `stop`) refer to the multi-splicer; standard `splice-*` keys are
also accepted. `runs` means full multi-splice passes, while `iterations`
means **splice** proposals, not the unrelated regular Auto `iterations`.
Other regular `[auto]` keys can be overridden here if needed. When using
`splice-search = "endpoint-auto"` or `"both"`, the named splicer also forwards
Auto's mutation mix, progressive/adaptive refinement, polishing, chain length,
shared refinement proposals and performance-statistics settings to its endpoint
Auto backend; the backend's own per-stage proposal budget is still determined
by `splice-iterations`.
 It reads `../splices/97-2/{203,408,switch,end}.txt` (or `.toml`)
when the input is `../n_levels/97-2.ltm`. Each goal must include a `[local]`
`objective` and `target-frame`; its `range`, region, object, velocity and
interaction constraints are interpreted by the same goal parser as
`--goal-config`. Splice names are not sorted and no automatic waypoints are
added. Use `splice-files = ["203.txt", "end.toml"]` to disambiguate extensions.

**Per-stage override precedence.** `[common]` and `[auto]` in the shared
config supply defaults. The level's `[multi-splicer]` overrides the shared
multi-splicer defaults. Each named `[local]` file overrides the goal fields
and applicable search settings **for that stage and for both backends**.
`[multi-splicer] search = "both"` remains authoritative: a stage file's
`search = "population"` does not disable Auto. An explicit CLI setting takes
precedence over the corresponding backend setting in the stage file.

Besides endpoint constraints (`target-frame`, `range`, `objective`, `region`,
`secondary-objective`, interactions, jumps and velocity windows), each stage
can override `iterations`, `beam`, `mutation-span`, `repair-steps`,
`repair-lookback`, `top-results` and `stagnation-rounds`. These configure both
Auto and Local as appropriate: e.g. `mutation-span = 64` sets both backends'
mutation spans, and `stagnation-rounds = 7` gives each selected backend a
seven-round patience (instead of the per-level Auto/Local limits). `rounds`
is supported only without independent Auto/Local stagnation, where it controls
the fixed internal search batch size. Stage-specific checkpoint/resume and
Local windows-only settings cannot be honored by a managed population search
and now fail explicitly instead of being silently ignored.

`simulate-enemies` is **per named splice**. Each `[local]` goal may set it
independently (`true` or `false`): Auto and Local search, checkpoint scoring,
loading saved checkpoints and enforcement of that stage's goal all run in its
selected physics world. An absent stage value inherits `[common]` (Auto's
usual default is enabled); an explicit CLI `--simulate-enemies` or
`--no-simulate-enemies` forces that choice for every stage. Both physics models
are built once and reused as needed; different stage settings do not conflict.

**Final replay safety:** the fully saved run is independently evaluated with
enemies enabled whenever any stage uses them (or the shared setting enables
them). A candidate that dies there cannot be published as a final improvement,
even if it was discovered by an enemy-disabled stage. Intermediate stage
checkpoints remain subject to their **own** stage setting, so an intentionally
enemy-disabled checkpoint may still be unsuitable for real playback until a
later stage successfully repairs the route.


**Standalone Hybrid Auto-budget parity:** `tas.py hybrid LEVEL SPLICE` now gives
its Auto phase the same per-worker endpoint proposal budget as
`tas.py auto LEVEL SPLICE` (including `[auto] endpoint-iterations-per-frame`),
instead of limiting Auto to `[multi-splicer] iterations`. Local retains
`[multi-splicer] iterations`. To choose a separate Auto budget explicitly, use
`--splice-hybrid-auto-iterations N` or `[multi-splicer] hybrid-auto-iterations=N`.
The shortcut displays the backend's normal Auto/Local round and worker updates,
while full multi-splicer search retains compact logging and its previous
per-phase budget defaults. The search remains stochastic, so equal Auto budgets
are not a promise of identical winners or equal elapsed times.

To use **both** Local population and endpoint Auto Hybrid at each named
checkpoint, set `splice-search = "both"`. **Endpoint Auto runs first**;
Local then starts from Auto's best stage candidate, or the original seed if
Auto did not improve on it. The per-branch `splice-iterations` budget is shared
approximately 50/50 between the two backends (the odd proposal goes to Local).
Results from both searches are merged into the same verified frontier. This
backend choice is available for named files only.

`splice-iterations` is the **same budget for every splice stage**, measured in
proposals per worker per internal search round. With `splice-search = "both"`,
it is shared between Local and endpoint Auto, rather than given to each twice.
`splice-rounds` runs the regular endpoint Auto campaign (or Local population
rounds) that many times **for every stage seed**. `runs` / `--auto-runs` counts
complete passes across all named splice files, and is independent of
`splice-rounds`. The total number of searches increases when a stage has more
seeds from its previous stage or two-back frontier. Actual distinct evaluations
can differ from proposal counts because of caching and Local repair steps.

#### Independent Auto and Local stagnation phases (named multi-splicer)

For each named splice seed, Auto runs until its **own** configured number of
consecutive non-improving backend rounds, then Local starts from Auto's best
admissible result and runs until **its own** separate stagnation limit. If
**either** phase improved the admissible stage objective, the pair of phases
restarts with Auto from the best candidate. The search advances to the next
seed/stage **only when an entire Auto -> Local pair finds no improvement**.
Each phase's counter resets on improvement in that phase, independently of the
other phase. Later stage constraints are still checked before a result may be
published. A route that improves only a partial progress key does not reset
stagnation; the saved stage comparison and full-run completion checks remain
strict. The best of every backend turn remains available to downstream stages.

In the shared `examples/config.toml`:

```toml
[multi-splicer]
search = "both"
iterations = 400
auto-stagnation-rounds = 10  # Auto's own consecutive unsuccessful rounds
local-stagnation-rounds = 50 # Local's own consecutive unsuccessful rounds
frontier = 3
runs = 5                     # full passes through all named splices
```

Keep level-specific `multi-splicer.toml` limited to `files = [...]`.
`iterations` is the number of proposals per worker per backend round, split
50/50 in `both` mode. Each Auto phase uses **one continuous Auto campaign**
and retains its survivor population across every round until its own
`auto-stagnation-rounds` limit. Each Local phase likewise uses **one continuous
Local population search** until its own `local-stagnation-rounds` limit.
No backend is restarted within its phase. If either phase improves the
admissible splice objective, repeat the pair from the updated candidate.
The `rounds` setting is **not used** in independent backend stagnation mode;
remove it from `[multi-splicer]`. It still controls fixed-round searches
when backend-specific stagnation is disabled. `runs` controls complete passes
through all named splices. Total computation varies with improvements.

Command-line overrides are `--splice-auto-stagnation-rounds N` and
`--splice-local-stagnation-rounds N`. Both must be positive for `search="both"`.
The older `stagnation-rounds` setting (shared full-cycle limit) is supported
for existing configurations only; remove it when using the two new settings,
since mixing old and new stagnation controls is an error. With all three set
zero, the original fixed `splice-rounds` behavior remains unchanged.

#### Stage search until stagnation (named multi-splicer)

To let each named splice continue until Auto and Local have exhausted the
improvements they can find, set the following shared configuration (the level's
`[multi-splicer]` file can still contain **only** `files = [...]`):

```toml
[multi-splicer]
search = "both"
iterations = 400            # proposals per worker per cycle, split Auto/Local
rounds = 1                 # backend campaign rounds per Auto or Local turn
stagnation-rounds = 5      # stop a stage seed after 5 full cycles with no gain
frontier = 3
runs = 5                   # complete passes through the named stages
```

Each **cycle** runs Auto, then Local starting from Auto's best admissible
candidate; the next cycle starts Auto from Local's best admissible candidate.
If either backend improves that seed's valid stage objective, the no-improvement
counter resets. Otherwise, it increments after *both* backends have tried.
The search moves to the next seed/stage after `stagnation-rounds` consecutive
cycles without an eligible improvement. Near misses can guide the search but
do not reset stagnation unless they satisfy the current stage's own goal.
Earlier splice objectives are independent search helpers, not constraints. A newly discovered route is measured against its own
starting candidate, not a possibly better historical checkpoint, so new routes
still have an opportunity to propagate. The regular `n-1` / `n-2` frontiers,
full-route verification, and stage checkpoint protection remain unchanged.

`iterations` and `rounds` are **per-turn granularities**, not fixed caps on
how many cycles a stage can run. With `search = "both"`, every full cycle has
up to `iterations * workers * rounds` nominal proposal slots, divided between
Auto and Local. Extra Local repair evaluations may occur. More than one seed
can be searched at the same stage, so total work is variable and potentially
much larger than before. For small passes, prefer `rounds = 1` initially.

`stagnation-rounds = 0` preserves the previous fixed-search implementation;
this makes adoption opt-in and leaves random, complexity, and physics splicing
unchanged. Use `--splice-stagnation-rounds N` to override it on the command
line. `--auto-runs` still controls full multi-splicer passes, not adaptive
cycles within a named splice.

With `splice-search = "both"`, Auto's returned candidates are ranked using the
named stage's endpoint objective before choosing Local's starting replay.
Feasible candidates outrank partial near-misses; the original stage seed is
retained as a fallback, and both backend results remain available to later
stages. This is sequential cooperation, not simultaneous execution.

Named multi-splice searches also write **playable per-stage best checkpoints**
next to the normal `--output` and `--replay-output` files. For example,
`--output wip/optim.ltm --replay-output wip/97-2.txt` with a splice file
`230.txt` saves `wip/optim_230.ltm` and `wip/97-2_230.txt` (likewise
`optim_switch.ltm` and `97-2_switch.txt` for `switch`). Files are created
when the initial route already satisfies a stage, and replaced only when that
stage's verified objective strictly improves. They retain their best value
across all outer rounds; existing stage files are not treated as resume inputs.
Stage checkpoints are **trial replays**, possibly incomplete and not necessarily
valid for the full route. The unsuffixed `optim.ltm` / `97-2.txt` remain
reserved for improvements that satisfy the full final verification.
Input, goal, config and final output filename collisions are rejected before
starting the search.

A `[auto:user-splice:temporary]` line is **yellow** on a terminal and signals
a new stage-only best, not a verified improvement to the completed run. Only
`[auto:user-splice] improved verified final replay` is green and saved.
Each stage also reports its backend search count, distinct evaluations, eligible
replays and stage-best objective. The shared budget and the two round limits
are printed at startup. Colors respect `[common] color = false` and `--no-color`;
redirected logs contain no ANSI escape codes.

Every stage also retains its best verified candidate frontier across rounds.
**Normal named multi-splicer searches always try the current input replay first**
(the path passed as the `auto` positional argument), even if an older saved
completed replay or preceding frontier has a better recorded stage score.
They then try distinct candidates from the preceding stage (**n-1**), the
stage before that (**n-2**), and any configured older lookback stages, without
removing existing frontier slots. The best candidate from each source runs
before lower-ranked candidates from the same source (n-1 rank 1, n-2 rank 1,
then n-1 rank 2, etc.). Duplicate replays are searched only once.
The seed log identifies `current input run` and each saved splice origin.
This may add one backend search per stage when the input differs from the
selected frontiers. An explicit `--splice-from-best` continues to start from
the requested saved splice; an interrupted search resumes its exact in-flight
backend first. With `--splice-each-best`, the saved best of that same stage
is also tried, after the input.

From the third stage, it tries seeds from both the preceding stage (**n-1**)
and the stage before that (**n-2**), reserving a slot for a distinct n-2 elite
even if n-1 won its local objective. This allows the later stage to avoid a
locally better but globally detrimental splice. Each saved checkpoint must
satisfy only its own goal; completed results still require canonical completion
and preserved persistent route-control events. More source branches may
increase total stage searches, but do not double the per-branch proposal budget.

Set `splice-directory = "../some/other/directory"` if the input or goal files
are elsewhere. A CLI equivalent is `--auto-splice-files 203,408,switch,end
--auto-splice-directory ../splices/97-2`. The `--auto-random-splice` flag is
not required when `splice-files` is set, although it remains supported.

After each stage the optimiser carries a bounded frontier of candidate replays
into the next stage. **Named splice goals are independent helpers**: a later
stage may improve by taking a different route, even if it no longer visits an
earlier stage's target. The active Auto/Local refinement leader and every saved
stage checkpoint are scored against **that stage's own goal only**. Stage-only
results remain separate from the unsuffixed completed replay. For completed
runs, actual canonical finish time (then exit proximity) determines the best
rank, regardless of intermediate splice objectives; persistent game controls
from the input run must still survive. A faster completion discovered at any
stage may be published after independent full replay verification. An earlier
canonical completion can be trimmed and verified. An already verified saved
completion cannot be replaced with an incomplete route. A better manually
edited completed input is copied to the saved final output before searching,
while the input itself remains seed 1. If a previous fully completed outer
campaign left a progress sidecar behind, a new invocation starts at round 1;
genuine interrupted backend state is still resumed. `splice-iterations`/`splice-rounds` control
search effort *per stage*. Per-file Local search tuning (such as `window`,
`passes`, or `restarts`) is not imported: only endpoint goal definitions are
read. Set `runs` to a finite number if you do not want an indefinite campaign.

Standalone `--splice-merge-only` and `--splice-merge-repair-only` take precedence
when `[multi-splicer] merge-repair-at-end = true` is configured. A standalone
fast merge never starts the end-of-run bridge-repair search. When two archived
sections have identical duration and checkpoint score, direct merging chooses
one deterministically instead of trying to compare their input-frame objects.

Standalone `--splice-merge-repair-only` also handles completed inputs and saved
continuations that finish **before** a later helper's target frame. The repair
scheduler uses an implicit neutral tail only for evaluating those helper goals;
it does not extend the verified completed movie on disk. Mutation-based bridge
searches never target frames after an already completed prefix's finish. One
unusable pair does not prevent attempts on other saved splice sections.

### Post-goal survival constraint (patch 57)

In a Local population goal or named splice `[local]` goal, `survive-after-goal = 12`
requires the player to remain alive through the **12 following input ticks**
after the accepted objective (arrival tick for earliest goals; `target-frame` for
fixed goals). Auto endpoint goals accept `[auto] survive-after-goal = 12` or
`--auto-survive-after-goal 12`. `0` (the default) leaves prior behavior unchanged.
A verified level completion during this interval counts as success. Death or
insufficient recorded frames (without completion) is not accepted as proof of
survival. Enable this only where the replay contains enough post-goal inputs.
The opt-in check uses independent native physics replay, not a heuristic.

### Individual versus cumulative splice gains (patch 58)

Stage best and summary lines distinguish **individual splice gain** (the elapsed
frames between this stage and the previous stage, measured on the **same replay**)
from **cumulative gain through this splice** (arrival-frame advantage versus
the positional input). An individual duration needs both neighboring helper
objectives to be feasible in that replay; missing goals are explicitly marked
as unmeasurable. Fixed-frame spatial goals show their objective's pixel delta
separately and never claim total time savings from an unchanged deadline.
Pixel gains are not accumulated across different axes or distance objectives.

### Compact merge logging (patch 59)

Fast and repairing merge passes now report the initial source, verified saved
improvements, failures that abort a pass, and one aggregate count summary;
they do not print each rejected or unchanged source/suffix pair. Use
`--splice-merge-verbose` or `[multi-splicer] merge-verbose = true` to restore
the previous per-pair detail while diagnosing a particular checkpoint.
Computation and merge ranking are unchanged by this logging switch.

### Short optimiser commands (patch 60)

`tas.py` is an **optional launcher** that calls the existing `optimize_replay.py`
CLI. It provides the usual input (`../n_levels/LEVEL.ltm`), output
(`wip/LEVEL.ltm`, `wip/LEVEL.txt`), workers (15), TOML and splice paths; the
underlying optimiser and its normal CLI remain fully supported.

```sh
./tas.py auto 53-4                   # whole-run Auto, 10 runs
./tas.py local 55-1 end              # local, 50 stagnation rounds
./tas.py random 55-1                 # random splicer with enemies
./tas.py goal 53-4 591               # endpoint Auto with a Local goal file
./tas.py multi 97-2                  # named multi-splicer, 50 rounds
./tas.py merge 88-4                  # standalone fast merge
./tas.py repair 88-4                 # standalone bridge repair
./tas.py loop 97-2 88-4              # run named multi on each level
./tas.py local 55-1 end --jaffar     # Local Jaffar option preset
./tas.py auto 53-4 --jaffar          # Auto Jaffar option preset
./tas.py multi 97-2 --dry-run        # inspect expanded command only
LEVEL=88-4 ./tas.py merge            # no repeated LEVEL argument
./tas.py multi 97-2 --auto-runs 5    # normal CLI flags pass through
```

Environment settings such as `TAS_WORKERS=15`, `TAS_CONFIG=examples/config.toml`,
`TAS_OUTPUT_TEMPLATE=wip/{level}.ltm`, `TAS_REPLAY_TEMPLATE=wip/{level}.txt`,
`TAS_INPUT_TEMPLATE=../n_levels/{level}.ltm`, and `TAS_MULTI_TEMPLATE`/
`TAS_GOAL_TEMPLATE` choose paths without rewriting your level configs.
`TAS_LEVEL` (or `LEVEL`) and `TAS_SPLICE` (or `SPLICE`) supply positional values.
With `TAS_INPUT_TEMPLATE` pointing at a manually edited replay, use a **different**
output template; the launcher refuses to overwrite its own input. `./tas.py --help`
lists all supported defaults. Normal optimiser flags appended afterward always
have the final word. No shell expansion or automatic use of wip files occurs.

### Required presence inside a region (patch 64)

An endpoint goal can require the player to be **alive inside an inclusive
rectangle at least once during an inclusive frame interval**, regardless of
whether a jump occurred there. In a `[local]` goal file (also used by named
splices and `--goal-config`):

```toml
[local]
require-region = "380:410,180:220"
require-region-frames = "440:500"
```

The interval defaults to `0:target-frame`; it must not extend beyond the
objective target. CLI equivalents are `--require-region` and
`--require-region-frames` for Local population and endpoint Auto. This is an
additional hard feasibility requirement only for **that** goal, not a
binding helper constraint for unrelated later named splices. The opt-in
reference path uses native simulation snapshots to check every eligible tick;
ordinary endpoints retain their fast native scan.

### Single-splice Auto ↔ Local (patch 65)

`both` runs the shared named-splicer Auto/Local backend on **one** Local goal,
without requiring a multi-splicer TOML list. Each native phase continues until
its own stagnation limit; a backend is restarted only when the other backend
found a changed seed. The goal file still determines the objective, editable
range and any hard physical requirements.

```sh
python3 optimize_replay.py both ../n_levels/88-4.ltm \
  --config examples/config.toml --goal-config ../splices/88-4/522.txt \
  --output wip/88-4.ltm --replay-output wip/88-4.txt --workers 15
# Or:
./tas.py both 88-4 522
```

Defaults: one outer pass; Auto stagnation 5, Local stagnation 20. Explicit
`--splice-auto-stagnation-rounds`/`--splice-local-stagnation-rounds` and
`--auto-runs` override them. Stage-only checkpoints remain separate in
`wip/LEVEL_522.ltm`, and only canonically verified completed replay gains can
replace `wip/LEVEL.ltm`. Existing `auto`, `local` and `goal` commands are unchanged.

### Airborne Shift cleanup on incomplete splice checkpoints (patch 66)

`--auto-clean-air-jumps` (or `[multi-splicer] clean-air-jumps = true`) now
checks **incomplete stage-best checkpoints** as well as completed outputs.
The old cleaning function returned immediately if a replay did not finish the
level, making it appear inert for pending splice gains. It still requires an
exact match of every observed physics tick, successful jumps, route-control
events, death/completion and score before stripping input pulses. It never
rewrites the active search population or any failed candidate.


### Splice search speed presets and round schedules

Named multi-splicer and single-splice `both` searches accept
`--splice-speed very-fast|vfast|fast|normal|slow`. `very-fast` and `vfast`
are aliases for **one stagnant round** in each Auto/Local phase; `fast` =
Auto 3/Local 10 stagnant rounds, `normal` = 5/20, `slow` = 10/50. These
are stagnation thresholds, not maximum total search rounds: improvements
reset the counter.
Use `--splice-round-speeds current,slow` to run outer round 1 with the current
configured stagnation limits, then outer round 2 (and subsequent rounds) with
slow patience. The schedule never changes ordinary splice lookback or physics.
The same options can be set in `[multi-splicer]` as `speed = "fast"` and
`round-speeds = ["current", "slow"]`. `--auto-runs` determines the number of
outer rounds; a schedule does not itself increase that number. Presets control
named splice phases, not standalone Auto endpoint or standalone Local.

In `hybrid`, `hybrid-restart`, and `hybrid-local-control`, `--splice-speed`
sets **stagnant hybrid cycle patience** instead: `very-fast`/`vfast`=1,
`fast`=3, `normal`=5, `slow`=10. This replaces the configured `hybrid-stagnation-cycles` value;
leave `--splice-speed` unset to use a manual value. `hybrid-cycles` remains a
hard cap and is **not increased** by a speed preset: for `slow` to allow 10
stagnant cycles, set `--splice-hybrid-cycles 10` or higher. Hybrid ignores
`--splice-round-speeds` and the old Auto/Local phase stagnation limits.


### Alternative named splice route

A per-level multi-splicer TOML can specify two independent ordered sequences:

```toml
[multi-splicer]
splice-files = ["72", "126", "179", "243", "289", "end"]
alt-route = ["72", "126", "185", "220", "289", "end"]
```

For normal searches, the routes are **interleaved at their first reconvergence**:
search any requested shared prefix once; search the primary divergent stages;
search the alternative divergent stages; search the reconvergence goal once
**from each branch**; then continue through the shared suffix, seeding it
from both branches. The shared suffix is searched just once, rather than
being exhausted before the alternative branch has even been explored.
Only replay-verified completed runs are promoted to the shared completed best.

At reconvergence, the higher-ranked goal result keeps the usual
`LEVEL_STAGE.ltm` (and TXT companion) if it improves the stored stage best.
The lower-ranked branch has its own replay at
`LEVEL_STAGE_other_route.ltm` (and companion TXT), with a route-identity
sidecar. It is kept across restarts and receives independent opportunities
in the shared suffix and the existing 64-replay frontier. For earliest-arrival
goals, lower-ranked usually means slower at the seam; spatial-only goals
rank by their configured objective rather than inventing a time saving.
A branch that cannot meet the rejoin goal does not erase the other branch;
both prefixes remain possible shared-suffix search seeds. Standalone
`--splice-merge-only` and `--ls-splice` retain their own non-search behavior.

For a short branch, specify only its **two seams** (existing primary splice
names, in primary-route order) and the new stages between them:

```toml
[multi-splicer]
splice-files = ["48", "85", "103", "137", "207", "275", "358", "403", "479", "527", "599", "end"]
alt-route = ["403", "482", "485", "527"]
```

This automatically inherits the prefix through `403` and suffix from `527`
onward, replacing primary `479` with `482 -> 485`. Only `482` and `485` are
searched during the alternative campaign. Both seam names must exist in
`splice-files` in that order; duplicate or overlapping branch names are
rejected. The original full-route notation ending in `end` remains supported.
CLI `--splice-alt-route 403,482,485,527` accepts the shorthand too.

Alternate routes do not impose helper goals on the primary route or change
normal stage lookback. Use `--start-at-splice 479` (alias `--splice-start 479`)
to skip searching the shared prefix through `403` and begin the primary
branch at its first divergent stage. The execution order is then
`479`, `482 -> 485`, `527` from **both** branch results, and finally
`599 -> ... -> end`. The initial seam `403` is not searched. If the requested
primary start is at or after reconvergence `527`, the earlier alternative
branch is skipped. If instead the requested start is **exclusive to the alternate
route** (e.g. `--start-at-splice 482`), only that alternate route is searched,
starting at `482` and continuing through `485`, the shared rejoin `527`, and
then the shared suffix to `end`. This works for both short and full alt-route
notations. Shared stage names retain the interleaved two-route behavior;
`--ls-splice` still lists both routes in full. `--splice-stop` and
`--splice-from-best` remain incompatible
with alternative routes. Each phase has its own backend checkpoint filename,
so its in-flight state cannot be mistaken for another branch's work.
