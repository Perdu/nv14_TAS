# n v1.4 TAS replay optimiser

This script combines a deterministic Python emulator for the relevant parts of
**n v1.4** with three replay-search strategies. The code was almost entirely 
generated by GPT 5.6.

- **`auto`** improves a known, completed whole-level speedrun or highscore replay.
- **`local`** optimises short sets of frames for a position or distance at a chosen frame.
- **`jump-pattern`** exhaustively searches a small number of physically successful jump pulses while preserving horizontal input.

The optimiser accepts either a combined n level/complex-replay text file or a
libTAS `.ltm` movie. It writes the result in the same format as its input, so an
LTM can be optimised and opened directly in libTAS without a separate conversion
step. The source file is never overwritten.

## Examples

All of the examples below use `examples/config.tml`. For details of all the configuration option refer
to the other sections.

Auto mode is used for optimising a whole level at once. Example:
```bash
python3 optimize_replay.py auto 'examples/91-1.txt' --config 'examples/config.toml' --output 'examples/91-1_optimised.txt'
```

An .ltm file can also be used:
```bash
python3 optimize_replay.py auto 'examples/91-1.ltm' --config 'examples/config.toml' --output 'examples/91-1_optimised.ltm' --replay-output 'examples/91-1_optimised.txt'
```

Local mode is used for varying direction inputs to maximise/minimise a particular goal when the jump 
frames are already set. There are also however additional options for adding in jump mutations.

Example for corner jump power maximisation:
```bash
python3 optimize_replay.py local 'examples/cj.txt' --config 'examples/config.toml' --output 'examples/cj_optimised.txt'
```

Jump-pattern mode is used for bruteforcing all possible jump combinations within a short frame range, 
such as jumping on top of a bounceblock. This mode does not edit direction inputs.
Example bruteforcing of all 2 and 3 jump combinations on top of a bounceblock:
```bash
python3 optimize_replay.py jump-pattern 'examples/bbjump.txt' --config 'examples/config.toml' --output 'examples/bbjump_optimised.txt'
```

## Requirements and setup

- Python **3.11 or newer**.
- No third-party packages are required to run the optimiser.
- `pytest` is required only to run the bundled test suite.

Extract the archive, open a terminal in the extracted directory, and confirm
that the command-line interface starts:

```bash
python optimize_replay.py --help
python optimize_replay.py local --help
python optimize_replay.py jump-pattern --help
python optimize_replay.py auto --help
```

On systems where `python` does not select Python 3, use `python3`. On Windows,
`py -3.11` or a newer installed version can be used in place of `python`.

The examples in this README use Bash-style `\` line continuations. In
PowerShell, put the command on one line or replace each `\` with a backtick.


## Input, output, frames and ticks

### Combined text input

A text `INPUT` must be UTF-8 and contain an adjacent n v1.4 level field and
complex replay field, normally in a record resembling:

```text
$level name#author##<level data>#<complex replay>#
```


### libTAS `.ltm` input

An `INPUT` whose suffix is `.ltm` is read as a libTAS movie. The optimiser uses
the single top-level regular-file member named `inputs`; editor branches such as
`inputs1` are not treated as the active movie. The first n replay frame is the
libTAS frame immediately after the first frame containing Space (`K20`). Setup
and menu input through that Space frame remain outside the replay and are
preserved.

The active keyboard field is mapped as follows:

| libTAS keysym | Key | n input |
|---|---|---|
| `ff51` | Left arrow | Left held |
| `ff53` | Right arrow | Right held |
| `ffe1` | Left Shift | Jump held; a rising edge generates jump trigger |

Only these three n controls are changed in output replay frames. Other keyboard
keys, mouse/controller fields and other per-frame data on retained lines are
preserved. So are archive members such as alternate input branches,
annotations and editor data, the pre-Space setup, and the movie's neutral
post-roll/padding. If an optimised replay becomes longer than the original
replay body, newly required frame lines contain only the n controls. If it
becomes shorter, output is refused rather than discarding unrelated input from
any source replay line that would be removed. The gzip/tar container is rebuilt,
so whole-file binary equality is not expected even when retained member data
is unchanged.

A raw LTM has no n level data, so the optimiser resolves a level identifier and
looks it up in `N v1.4 + NReality levels.txt`:

1. `--level-id NN-N`, when supplied;
2. an identifier embedded by an earlier output; or
3. the exact filename stem, for example `00-0.ltm` implies `00-0`.

If the name is not sufficient, pass `--level-id`. An explicit identifier that
conflicts with embedded metadata is rejected.

Use `--levels-file FILE` to select the level database directly. Otherwise the
optimiser searches for `N v1.4 + NReality levels.txt` in a few likely locations.


For a raw movie, replay length is inferred by removing trailing frames with no
Left, Right or Shift input after the Space boundary. The removed neutral frames
remain as libTAS post-roll. If that inference would also remove intentional
idle replay frames, use `--ltm-postroll N` to declare exactly how many final
rows of the active input log are padding. For example, `--ltm-postroll 3` keeps
every post-Space row except the final three, while `--ltm-postroll 0` keeps
every post-Space row in the replay. `N` must leave at least one replay frame.
The explicitly excluded rows are authoritative post-roll and are preserved
unchanged, even if they contain later keyboard or device input.

An optimiser-written LTM instead contains `nv14_optimizer.json`, tied to the
active `inputs` content by SHA-256, recording the exact replay start, tick count,
level ID and complete level record. Without an explicit post-roll override,
this preserves intentional replay-idle frames and makes later passes
self-contained; the level database is no longer needed unless `--levels-file`
is explicitly given. If libTAS or another tool later changes `inputs`, the
stale exact replay boundary is ignored with a warning and the raw-movie rules
are used again; a still-valid embedded level identity remains available.

### Output files

All optimisation commands require `-o FILE` or `--output FILE`. A text input
writes a complete combined level/replay record. An LTM input requires an `.ltm`
output and rebuilds that movie with the verified replay in its active `inputs`
member. A text input cannot produce LTM output because it provides no movie
template.

`--replay-output FILE` additionally writes only the packed replay string. It is
optional and works with either source format; a replay-only file is not itself a
valid optimiser input until it is merged into a combined record or movie.

The input, main output and replay-only output must all be different files. The
output directory must already exist. Writes use an atomic replacement, and
verified live checkpoints are used where the mode supports them.

Every LTM must contain exactly one top-level `config.ini` with one numeric value
for each of `frame_count`, `framerate_num`, `framerate_den`, `length_sec` and
`length_nsec`; both frame-rate values must be positive. The output synchronises
the frame count and duration with the edited active input log, respecting valid
per-frame libTAS timing fields where present.

### Local and jump-pattern frame convention

Frame numbers are zero-based. `--target-frame N` applies replay inputs `0`
through `N`, inclusive, then evaluates the resulting state. Thus target frame
71 means 72 input steps have been simulated.

### Auto completion convention

Auto uses n's whole-replay convention instead. A body of `N` serialized inputs
is simulated with exactly one implicit neutral input at step `N`. A canonical
Auto replay must complete on that neutral sentinel, so its finish tick is also
the number of serialized inputs written.

If the supplied replay contains unused inputs after an earlier completion, Auto
first trims them and verifies the canonical sentinel-ending form.

If the game sets completion and then kills the ninja later in the same object
collision traversal, death on that exact completion tick is accepted; a death
on any earlier tick is not.

## Quick start and choosing a mode

| Goal | Mode | Source replay requirement | What is changed |
|---|---|---|---|
| Improve a complete route automatically | `auto` | Must be a live, completed route in the selected emulator model | Whole-route semantic mutations, retimes and repairs |
| Improve position or distance at a known frame | `local` | Need only remain alive through the target frame | Small contiguous or sparse frame sets |
| Exhaustively retime a few jumps | `jump-pattern` | Need only remain alive through the target frame | Jump-held input in one continuous range; horizontal input is preserved |

## Common options

The command shape is:

```text
python optimize_replay.py MODE INPUT [OPTIONS]
```

`MODE` must be the first argument and must be `auto`, `local` or
`jump-pattern`. There is no implicit default mode and no legacy `--mode`
option.

| Option | Meaning |
|---|---|
| `INPUT` | Combined custom-level/replay text file or libTAS `.ltm` movie. This remains positional even when TOML is used. |
| `-o FILE`, `--output FILE` | Required same-format output, except with `--list-objects`. Must differ from the input; an LTM input requires an LTM output. |
| `--levels-file FILE` | Level database for a raw LTM. Usually discovered automatically; explicitly supplying it also overrides an embedded level record. LTM-only. |
| `--level-id NN-N` | Level ID when it cannot be inferred from an LTM filename or embedded metadata. LTM-only. |
| `--ltm-postroll N` | Raw-LTM replay boundary override: treat exactly the final `N` active-input rows as padding. `0` keeps every post-Space row. LTM-only. |
| `--replay-output FILE` | Optional replay-only output. Must differ from both other paths. |
| `--config FILE` | Load defaults from a TOML file. Explicit scalar CLI options take precedence. |
| `--retime START:DELTA` | Apply a fixed-length transition-suffix retime before the selected search. Repeatable. |
| `--list-objects` | Print stable target and interaction selectors, then exit. No output or target frame is required. |
| `--workers N\|auto` | Select a positive process count. `1` always forces serial; `auto` is the default. |
| `--simulate-enemies` | Enable the supported enemy model. |
| `--no-simulate-enemies` | Disable it. Auto defaults to enabled; Local and jump-pattern default to disabled. |

Only options valid for the selected mode are accepted. For example, Local
rejects `--iterations`, jump-pattern rejects `--seed`, and Auto rejects
`--target-frame`. The removed `--non-strict-shapes` option is also rejected.

## Auto mode

Auto is a reference-guided whole-level optimiser. It starts from a verified
completed replay, tries route-level changes, and repairs the first broken jump,
contact or route-control dependency. Its search includes suffix and boundary
retimes, horizontal pulses, jump-pulse edits, trajectory splices, sparse
direction changes and bounded all-input repair.

The source replay is always retained as a candidate. A speedrun result therefore
cannot be slower than the verified source, and every result is packed, decoded
and simulated again before it is written. On an equal primary result, exit
proximity immediately before the neutral sentinel is used as a tie-break, so an
equal-time or equal-score alternate may replace the source.

### Speedrun and highscore objectives

`--auto-objective speedrun` is the default and minimises raw completion tick.

`--auto-objective highscore` maximises the replay's relative timer contribution:

```text
highscore value = 80 * collected gold - finish tick
```

Highscore mode may use time after the source finish to reach extra gold.
`--auto-max-extra-ticks N` sets that editable extension. When omitted, the
default is up to 80 ticks, reduced to zero when the source already has all gold.
Use `--auto-require-reference-gold` when every exact gold collected by the
verified post-retime source must remain collected. Without it, Auto may
intentionally trade a source gold for enough time saving to improve the score.
Other exit switches, locked-door switches and trapdoors are route-state signals,
not universal preservation constraints: a fully simulated completed alternate
may legitimately skip an optional control or trigger a harmless one.

### Search rounds and workers

Each worker runs one complete seeded Auto search with its own
`--iterations` budget. With multiple workers, completed searches form a small
population: the best half (rounded up) seed the next round, while idle slots may
begin one-generation-ahead speculative work.

- `--workers auto` selects up to eight available CPUs.
- `--auto-runs 1` performs one bounded round.
- `--auto-runs N` performs `N` population rounds.
- `--auto-runs 0` continues indefinitely until Ctrl+C.
- `--workers 1` uses the serial campaign path and restarts each round from the
  current winner.

The total nominal macro budget for a bounded campaign is
`iterations * workers * auto-runs`. Local repair simulations are reported
separately and can dominate runtime.

### Recommended long campaign pattern

```bash
python optimize_replay.py auto run.txt \
  --auto-objective speedrun \
  --iterations 10000 \
  --beam 64 \
  --max-retime 3 \
  --auto-repair-local-steps 2000 \
  --auto-campaign-local-steps 20000 \
  --auto-frame-ahead-repair-multiplier 50 \
  --workers 8 \
  --auto-runs 0 \
  --seed random \
  --output run_next.txt
```

This is intentionally unbounded. Auto writes each new globally best verified
result immediately. Ctrl+C cooperatively stops the campaign, writes the best
verified result available, and exits with status 130.

If full fidelity is needed, retain the default enemy simulation. Add
`--no-simulate-enemies` only for an explicitly exploratory run whose result will
later be checked in the full model and in the game.

### Auto mutation range

`--range START:END` restricts eligible mutation seams or starts. It is not a
strict immutable-frame mask: an allowed suffix mutation can still alter later
frames beyond `END`. Auto accepts only one continuous range.

Open-ended, full and single-frame forms are accepted, for example
`--range :250`, `--range 100:`, `--range :` and `--range 175`.

### Auto tuning

- Increase `--iterations` for more proposals per independent search.
- Increase `--beam` for diversity, at greater memory and candidate-management
  cost.
- Increase `--auto-repair-local-steps` when promising edits repeatedly reach a
  broken jump or contact that the default repair cannot solve.
- Increase `--auto-campaign-local-steps` when a whole repair campaign ends
  before exploring enough alternatives.
- Increase `--auto-frame-ahead-repair-multiplier` when frame-ahead candidates
  deserve substantially deeper repair. A value of `1` disables this bonus.
- Use `--auto-no-deterministic` for repeated stochastic campaigns when the
  structured bootstrap has already been thoroughly explored.
- Keep a printed integer seed to reproduce a useful `--seed random` campaign.

Both repair ceilings count fresh local simulations. A base value of `0` means
unlimited; use it cautiously. The campaign ceiling is soft and checked between
repair attempts. Alignment tolerances guide proposals only: candidates still
receive complete simulation and final verification.

## Local mode

Local search is a greedy overlapping-window optimiser, not a global exhaustive
proof over the whole range. It exhaustively searches each small frame set,
accepts a useful candidate as the incumbent for later windows, and refines the
result across passes. Window order can therefore affect the final result.

Frames after the last mutable frame are replayed unchanged through the target
frame, so delayed effects are included in scoring. `--target-frame` is required.
If `--range` is omitted, every frame from 0 through the target frame is mutable.

### Objectives

```bash
python optimize_replay.py local run.txt \
  --target-frame 161 \
  --range 100:161 \
  --objective min-distance \
  --target-point 732,108 \
  --window 4 \
  --passes 3 \
  --output run_optimised.txt
```

See [Objectives, targets and coordinate constraints](#objectives-targets-and-coordinate-constraints)
for all positional objectives and hard coordinate windows.

### Mutable ranges

Local accepts one or more inclusive ranges:

```text
--range 90:105
--range 90:105,250:280
--range :105
--range 250:
--range :
--range 90
```

Multiple intervals are sorted and overlapping or adjacent entries are merged.
With disjoint ranges:

- contiguous windows stay inside one interval and never bridge an excluded gap;
- sparse windows select from the union and may coordinate frames in different
  intervals while every gap input remains fixed;
- `--window-span` measures the real inclusive distance from the first selected
  frame to the last, including any excluded gap;
- direction-only jump mutations affect only complete source jump pulses wholly
  contained in one interval.

The range end cannot be later than the target frame.

### Input alphabets

`--local-inputs all` is the default. Each mutable frame can be Left, Neutral or
Right, crossed with jump released or held: six theoretical choices per frame.
The raw upper bound for a `W`-frame window is `6^W`, although inactive-jump,
death and duplicate-state pruning usually remove many branches.

`--local-inputs direction` searches only Left, Neutral or Right and preserves
the replay's jump-held sequence: `3^W` theoretical choices. Every rising
jump-button press through the target frame is treated as a required successful
`Player.jump()` event. If the reference contains an inactive press, Local may
repair it through horizontal changes, but it will not silently output a run
that still misses a required press.

Direction-only mode is usually the practical choice for wider windows when the
jump timing is already good.

### Window shapes

`--window N` sets the number of mutable frames searched together. The default is
4. If the requested size is larger than the available mutable set, it is
reduced to the available size.

`--window-shape` controls which frames form a window:

| Shape | Behaviour |
|---|---|
| `contiguous` | Ordinary overlapping consecutive windows. This is the default. |
| `sparse` | Randomly samples `--window` mutable frames; intervening inputs stay fixed. |
| `mixed` | Alternates sparse, contiguous, sparse, contiguous passes, starting sparse. |

For sparse passes:

- `--window-span N` limits the inclusive first-to-last frame span. It must be at
  least the effective window size. Omitting it allows the full mutable range.
- `--windows-per-pass N` controls how many distinct random frame sets are tried.
  Its default is the number of ordinary contiguous windows. Sampling cannot
  exceed the number of feasible distinct sets.

`--window-span` and `--windows-per-pass` are invalid with a purely contiguous
shape. A contiguous pass with no accepted change can stop that trajectory
early; sparse searches still sample later passes because they may select new
frame sets.

### Window order and independent trajectories

`--window-order` controls traversal:

| Order | Behaviour |
|---|---|
| `forward` | Visits windows by increasing temporal centre. Default. |
| `reverse` | Visits them in the opposite order. |
| `random` | Runs `--restarts N` independent shuffled trajectories, each starting from the untouched post-retime replay. |
| `mixed` | Compares one forward trajectory, one reverse trajectory and `--restarts N` random trajectories. |

`--window-shape mixed` and `--window-order mixed` are independent controls. The
first mixes sparse and contiguous passes inside a trajectory; the second mixes
different trajectory orders.

Use an integer `--seed N` to reproduce sparse sampling or random/mixed order.
When randomness is needed and no seed is supplied, Local generates and prints a
seed. The literal `--seed random` is Auto-only and is rejected by Local.

### Direction-only jump mutation

Random or mixed direction-only searches can vary complete source jump pulses
before each random restart:

```bash
python optimize_replay.py local run.txt \
  --target-frame 300 \
  --range 120:300 \
  --objective max-x \
  --local-inputs direction \
  --window-order mixed \
  --restarts 20 \
  --jump-start-mutation 2 \
  --jump-length-mutation 3 \
  --immutable-jumps 142:both,210:start,245:length \
  --output run_optimised.txt
```

- `--jump-start-mutation X` samples each eligible start offset in `[-X,+X]`.
- `--jump-length-mutation Y` samples each eligible hold-length offset in
  `[-Y,+Y]`, keeping length at least one and valid released gaps between pulses.
- `--immutable-jumps FRAME[:PROPERTY],...` preserves `start`, `length` or
  `both` for named post-retime source pulses. A bare frame means `both`.

Jump mutation requires `--local-inputs direction`, a `random` or `mixed` window
order, and at least one non-zero mutation bound. An unmutated control trajectory
is retained so enabling mutation cannot discard the original jump timing.

### Optional physics pruning

`--physics-prune` enables a horizontal kinematic branch-and-bound in
direction-only mode. It is safe only when the future path cannot acquire a
horizontal boost from an object or collision. Launch pads, bounce blocks,
thwomps and unusual collision boosts can violate that assumption. Leave it off
unless the searched section is understood. It principally helps `max-x`,
`min-x` and searches with an x window.

### Local constraints and checkpoints

Local can require or prohibit persistent route interactions; see
[Required and forbidden interactions](#required-and-forbidden-interactions).
Hard interaction repairs and required successful jump presses outrank the
positional objective. `--minimum-improvement D` applies only to ordinary
positional gains; use a non-negative value in normal searches.

Every accepted candidate that becomes the best checkpoint so far is packed,
decoded, simulated from frame zero and checked against all hard constraints
before it replaces the output. This protects useful progress during long serial
or multi-worker searches.

## Jump-pattern mode

Jump-pattern is specialised for a route whose horizontal inputs are already
useful but whose jump timing needs exhaustive search.

Inside one continuous `--range`, it replaces only the jump-held stream with
non-overlapping pulses represented by `start frame + hold length`. Left/right
input is preserved frame-for-frame, and inputs outside the range are unchanged.
At least `--minimum-gap` released frames separate pulses.

A pulse counts toward `--jumps` only when its rising edge actually invokes
`Player.jump()` in the emulated state. Inactive airborne button presses are
discarded rather than counted as jumps.

### Jump counts and lengths

```text
--jumps 2        exactly two successful jumps
--jumps 2:4      two, three or four successful jumps
--jump-length 5  exactly five held frames per pulse
--jump-length 2:10
--jump-length 2: maximum length that fits
```

Defaults are `--jumps 2:3`, `--jump-length 1:`, `--minimum-gap 1` and
`--top-results 10`.

The optimiser prints the retained ranked patterns and writes the best one.
Frames after the mutable range are simulated unchanged through
`--target-frame`, so the objective can measure a delayed landing or boost.

### Fixed jump starts

`--fixed-jump-frames F1,F2,...` requires selected rising edges in the
post-retime source to remain at exactly those frames while still searching
their hold lengths. Movable pulses may appear before, between or after them.

Each fixed frame must:

- lie inside the jump-pattern range;
- be a jump rising edge in the source replay;
- permit a physically successful jump in every retained branch;
- fit the configured jump-count, hold-length and minimum-gap constraints.

Jump-pattern has no random seed. Its search is exhaustive over physically
distinct reachable states within the requested pulse bounds. Multiple workers
partition exact frontier states; tied retained ordering can differ between
serial and parallel runs, but ranking and state verification remain exact.

Jump-pattern does not support disjoint ranges or Local interaction constraints.
Its search space grows combinatorially, so narrowing the range, jump count and
maximum hold length—or fixing known starts—has the largest effect on runtime.

## Objectives, targets and coordinate constraints

Local and jump-pattern share these target-frame objectives:

| Objective | Meaning |
|---|---|
| `max-x` | Move as far right as possible. |
| `min-x` | Move as far left as possible. |
| `max-y` | Maximise y; n's screen coordinates increase downward. |
| `min-y` | Minimise y; move upward. |
| `min-distance` | Minimise Euclidean distance from the player's centre to a point or object anchor. |

`min-distance` requires exactly one of:

```text
--target-point X,Y
--target-object SELECTOR
```

### Object selectors

List a level's stable selectors and coordinates before choosing one:

```bash
python optimize_replay.py local run.txt --list-objects
```

Selectors use stable per-type indices in level-data order:

```text
TYPE
TYPE:INDEX
TYPE:any
TYPE:INDEX.ANCHOR
TYPE:any.ANCHOR
```

Examples:

```text
exit                 one unambiguous exit; defaults to its door
exit:0.door          first exit's door
exit:1.switch        second exit's switch
exit:any.door        nearest exit door
switch:1             switch belonging to exit:1
gold:7               eighth gold
gold:any             nearest gold
bounceblock:0        first bounce block's centre
```

A bare type is accepted only when exactly one matching object exists. Use an
explicit index to choose an identity or `:any` to target the nearest matching
object. Exits expose `.door` and `.switch`; most point-like types expose
`.center`. Supported target types are `gold`, `bounceblock`, `launchpad`,
`turret`, `floorguard`, `player`, `drone`, `onewayplatform`, `thwomp`,
`testdoor`, `hominglauncher`, `exit`, `mine`, plus the `switch` pseudo-type.
`--list-objects` is authoritative for the level.

### Coordinate windows

`--x-window` and `--y-window` are inclusive hard constraints at the target
frame. They can accompany any Local or jump-pattern objective:

```bash
python optimize_replay.py local run.txt \
  --target-frame 161 \
  --range 100:161 \
  --objective max-x \
  --y-window 98.7:98.9 \
  --window 4 \
  --passes 3 \
  --output run_optimised.txt
```

Accepted forms include:

```text
--x-window 500:700
--x-window :700
--x-window 500:
--x-window 600
```

A single value requests exact binary64 equality. A narrow interval is usually
more practical than exact floating-point equality. Candidates that die or fall
outside either coordinate window are infeasible.

## Required and forbidden interactions

These controls are Local-only and are checked through the target frame,
including immutable prefixes, excluded range gaps and unchanged suffixes.
Repeat an option to combine several conditions with AND.

### Requirements

```bash
python optimize_replay.py local run.txt \
  --target-frame 400 \
  --range 200:400 \
  --objective max-x \
  --require-interaction gold:7 \
  --require-interaction switch:0 \
  --require-interaction testdoor:2 \
  --window 6 \
  --passes 3 \
  --output run_optimised.txt
```

Supported positive requirements are:

| Selector | Requirement |
|---|---|
| `gold:INDEX`, `gold:any` | Collect the exact gold, or at least one gold. |
| `switch:INDEX`, `switch:any` | Activate the exact exit switch, or at least one. |
| `exit:INDEX.switch` | Alias for the corresponding `switch:INDEX`. |
| `testdoor:INDEX`, `testdoor:any` | Activate the exact locked TestDoor switch, or at least one locked-door switch. |

Bare `gold`, `switch` and locked `testdoor` selectors are also accepted when
exactly one valid matching interaction exists.

`--require-reference-interactions` derives exact requirements for every gold,
exit switch and locked-door switch used by the post-retime reference replay
through the target frame. It preserves identities, not merely counts.

### Avoidances

Supported persistent avoidances are:

| Selector | Prohibition |
|---|---|
| `gold:INDEX`, `gold:any` | Do not collect that gold, or any gold. |
| `switch:INDEX`, `switch:any` | Do not activate that exit switch, or any exit switch. |
| `exit:INDEX.switch` | Alias for the corresponding switch. |
| `testdoor:INDEX`, `testdoor:any` | Do not activate that persistent locked-door or trapdoor interaction, or any such TestDoor. |
| `trapdoor:INDEX`, `trapdoor:any` | Do not trigger that trapdoor, or any trapdoor. The index is the stable **testdoor** index. |

Bare avoidance types are accepted only when exactly one valid persistent match
exists.

For a requirement, `TYPE:any` means at least one matching object satisfies the
condition. For an avoidance, it means every matching object is forbidden.

Ordinary proximity doors are not valid persistent interaction constraints: they
can close again, so target-frame state does not prove whether they were touched.
Trapdoors can be forbidden because triggering one leaves persistent state, but
they cannot be positive requirements.

An explicit requirement may ask Local to repair an interaction absent from the
source. A forbidden interaction already present in the source may likewise be
repaired. The search will not exchange one exact missing or violated identity
for a different one merely to improve position. For a distant new interaction,
it is often effective to minimise distance to it first, then enforce it as a
hard requirement in a later pass.

## Replay retiming

Every mode accepts repeatable pre-search retimes:

```text
--retime START:DELTA
--retime whole:DELTA
```

`DELTA` must be `-3`, `-2`, `-1`, `+1`, `+2` or `+3`.

`START` must be an actual held-input transition frame. Transitions compare the
Left/Right/Jump-held tuple with the preceding frame; jump-trigger bits are
ignored. Frame zero is a transition only when the replay begins non-neutral.
`whole` selects the first current transition.

Every transition at `START` and later moves by the same delta while total replay
length remains fixed. A negative delta advances the suffix; a positive delta
delays it. A retime is rejected if it would overtake the preceding transition,
move before frame zero, or push a transition beyond the replay end.

Repeated specs are applied sequentially, so later `START` values are validated
against the already-retimed replay:

```bash
python optimize_replay.py local run.txt \
  --retime whole:-1 \
  --retime 120:+1 \
  --target-frame 300 \
  --range 200:300 \
  --objective max-x \
  --output run_optimised.txt
```

In Local, the original source is printed as the baseline and the retimed replay
is the search seed. Reference-derived interactions come from the post-retime
seed. In Auto, the retimed replay is the route that must pass source completion
verification and from which reference gold is derived.

## TOML configuration

Use `--config FILE` to provide defaults while keeping the mode and input
positional:

```bash
python optimize_replay.py local run.txt \
  --config examples/config/local.toml \
  --output run_optimised.txt
```

TOML may contain legacy top-level option keys, a `[common]` table and separate
mode tables. Only the selected mode table is applied; other known mode tables
may coexist for later runs.

```toml
[common]
workers = 8
simulate_enemies = false
replay_output = "run_optimised.replay"

[local]
target_frame = 300
range = ["90:105", "250:280"]
objective = "min-distance"
target_object = "exit:0.door"
window = 6
window_shape = "mixed"
window_span = 96
windows_per_pass = 50
window_order = "mixed"
restarts = 10
seed = 123456
require_interaction = ["switch:0", "testdoor:1"]
avoid_interaction = ["trapdoor:any"]
```

LTM resolution and output paths are also ordinary common options. For example:

```toml
[common]
levels_file = "external/N v1.4 + NReality levels.txt"
level_id = "00-0"
ltm_postroll = 3
output = "recording_optimised.ltm"
replay_output = "recording_optimised.replay"
```

`levels_file`, `level_id` and `ltm_postroll` are rejected when `INPUT` is not an
LTM. `ltm_postroll` is normally needed only for the first pass over an ambiguous
raw movie; remove it on later passes to use the exact embedded tick count.
The level options can normally be omitted after the first v2.70 pass because
the output movie embeds the exact level record and identifier.

Rules:

- Effective precedence is built-in defaults, top-level keys, `[common]`, the
  selected mode table, then explicit CLI scalar options.
- Repeatable CLI options (`retime`, `require_interaction` and
  `avoid_interaction`) append to configured arrays rather than replacing them.
- A CLI `--range` is scalar and replaces a Local TOML range array.
- Keys may use underscores or CLI-style hyphens.
- In a mode table, the mode prefix may be omitted: `objective` under `[auto]`
  means `auto_objective`, and `runs` means `auto_runs`.
- `[jump_pattern]` is accepted as an alias for `[jump-pattern]`, but do not
  define both.
- The mode, input and config path cannot themselves be supplied by TOML.
  `output`, `replay_output`, `levels_file`, `level_id` and `ltm_postroll` may be
  supplied.
- Unknown sections, unknown keys, invalid types and settings belonging to
  another mode are errors rather than silently ignored.
- Put only genuinely shared settings in `[common]`; an Auto-only key there will
  make the same file invalid when selected with Local or jump-pattern.
- TOML paths are resolved relative to the process working directory, not the
  config file's directory.
- `workers` is either the string `"auto"` or a positive integer; numeric zero is
  not an accepted CLI/TOML spelling.

Convenient arrays are supported:

```toml
[common]
retime = ["whole:-1", "120:+1"]

[local]
target_point = [470.0, 432.0]
x_window = [0.0, 500.0]
range = ["90:105", "250:280"]
immutable_jumps = ["42:both", "73:start"]

[jump-pattern]
jumps = [2, 3]
jump_length = [1, 8]
fixed_jump_frames = [42, 73]
```

TOML has no null value. Use strings for open-ended values, such as
`x_window = ":500"` or `jump_length = "1:"`.

Boolean destination names are often the clearest TOML spelling:

```toml
[auto]
deterministic = false
all_input_repair = false
require_reference_gold = true
```


## Seeds, workers, checkpoints and interruption

### Seeds

- Auto defaults to deterministic seed `0`.
- Auto accepts an integer or `--seed random`; the latter chooses and prints one
  fresh 64-bit master seed.
- Local accepts an integer seed. When a sparse or random/mixed search needs a
  seed and none is supplied, it generates and prints one.
- Jump-pattern is exhaustive and has no seed option.

Worker seeds are deterministically derived from the master seed and worker
tasks. Keep the printed master seed and the same configuration to reproduce a
campaign.

### Workers

`--workers auto` is mode-aware:

- Auto uses up to eight independent CPU-bound searches per round.
- Jump-pattern adapts to the number and cost of independent frontier branches,
  up to eight available CPUs.
- Local first parallelises independent forward/reverse/random trajectories. A
  lone sufficiently expensive trajectory may instead split a safe DFS frontier
  within its current window. Small searches may deliberately remain serial.

`--workers 1` is the reliable low-overhead choice for tiny searches and exact
performance comparisons. Multiprocessing is supported on Windows, macOS and
Linux.

### Checkpoints and Ctrl+C

- Auto checkpoints every new global verified best. On Ctrl+C it retains and
  writes the best verified result, then exits with status 130.
- Local checkpoints new best candidates from the parent process after clean
  frame-zero verification. If interrupted, the latest completed checkpoint
  remains on disk, though a run interrupted before its first improvement may
  not yet have created output.
- Jump-pattern writes only after the exhaustive search finds and verifies a
  feasible winner; interrupting it before completion normally produces no new
  output.

The same checkpoint rules apply to LTM runs. Every accepted Auto or Local
checkpoint is rebuilt atomically from the original movie template, with its
exact replay/level metadata refreshed; `--replay-output`, when requested, is
updated to the same packed replay.

All multiprocessing workers leave Ctrl+C handling to the parent process to
avoid competing writes or noisy child tracebacks.

## Emulation scope and fidelity

Static and core physics are always enabled. The emulator includes the parts of
n v1.4 used by the bundled search and regression corpus, including:

- Player Verlet integration and standing, running, skidding, jumping, falling
  and wall-sliding states.
- Source-order object, thinker, player, object-collision and tile-collision
  processing.
- All standard static tile shapes (IDs 0–33), including slopes, curved tiles and
  half tiles.
- One-way platforms, launch pads, bounce blocks and thwomps.
- Gold, mines, exits and exit switches.
- Locked, proximity and trap `TestDoor` behaviour.
- Optional floorguards, zap/laser/chaingun drones, homing launchers and gauss
  turrets.
- Mutable object state cloning, ordering and branch isolation.

The enemy toggle controls only the supported optional enemies listed above;
thwomps and the static/interactive objects remain simulated.

| Mode | Enemy default |
|---|---|
| Auto | Enabled, because whole-route completion should use the fuller model. |
| Local | Disabled, for cheaper targeted searches unless explicitly requested. |
| Jump-pattern | Disabled for the same reason. |

Choose the same enemy setting used to create or verify the source trace. A
result found with enemies disabled is valid only in that reduced model until it
is checked again with enemies enabled and in n v1.4.

Intentionally omitted are unlisted enemy/object behaviours, presentation-only
sound/animation/GUI behaviour, death-ragdoll simulation after a terminal
branch, and the episode countdown time-out system. Unknown static tile shapes
are errors.

Final packed output is always decoded and simulated cleanly from frame zero in
the selected model. This detects serialization differences, deaths, hard
constraint failures and state mismatches before a result is accepted.

separate heuristic beam search, not one of the three replay-optimisation modes.
