Here is a TAS of the N game running on Ruffle, using libTAS. In the attached archive, you will find:
- the SWF of the game, and a patched version displaying more information when running (among other things)
- a bruteforcer (in tas\ optimiser/) that you can use to optimize a route. This bruteforcer contains a rewrite of the game's engine in C for faster execution.
- the binaries for libTAS and ruffle, so you can run them locally, in case you need to verify the run against the original game (you probably don't, use the simulator)
- techniques/README.md: a list of techniques and glitches we found in the game and use for the TAS.
- a libTAS ltm file for the level we are TASing.
I want you to try to optimise this TAS for the attached level. The goal is fastest termination of the level, which is done by taking the doorswitch, then reaching the exit door. You can be creative and attempt to apply the techniques found in the README when it seems relevant. Most notably, cj, rcj and bwj (including on bounceblocks and thwumps) are usually the best way to gain time. Study the level to estimate where they could lead to faster routes. Clips are mostly not possible, or probably already tested by humans for this level.
A good way to optimise the TAS is to do a splice run of the optimiser: using local mode to reach key points as early as possible (+ considering other factors such as speed and positioning for the rest of the run), then continuing gradually (to the next splice) until the end of the level. Study the level carefully to identify bottlenecks in the run that you can use to splice the run. You do not need to repair the whole run when optimizing earlier portions: just keep improving the run until the end is reached. Auto mode was already run for this level.
When discussing the result, show the demo string of the run you're mentioning, in the long form (including the level data so it can be copy-pasted into the in-game replay viewer), when you can, even if these routes are currently incomplete or failing.
